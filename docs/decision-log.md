# Decision log

Every decision this app has made, in the order it made them, with the
measurement or the bug behind each one. It was `CLAUDE.md` until session
B, when the rules that are load-bearing — the ones that exist to stop a
bug coming back — moved into [CLAUDE.md](../CLAUDE.md) as rules, and
everything else stayed here as history.

Nothing was dropped in that move and nothing was rewritten. Entries are
kept as they were written, which means:

- **They contradict each other on purpose.** A later entry that begins
  SUPERSEDES is the current answer; the one it supersedes is left in place
  because the reasoning that was wrong is the useful part.
- **Entries before the rename say LyriSync** and `com.lyrisync.lyrisync`,
  because that is what the app was called when they were written.

Read [CLAUDE.md](../CLAUDE.md) for what still binds. Read this for why.


- Stack: Python + PySide6, MVP first, possible Swift rewrite later touches UI only
- Spotify integration: local AppleScript polling (~300ms), not Web API
- Lyrics: LRCLIB, cache locally keyed by Spotify track ID, fallback chain synced → plain → "no lyrics"
- Architecture: three separated components (player monitor, lyrics provider, UI); monitor and provider know nothing about the UI
- Milestone order: monitor script → terminal-synced lyrics → floating window → polish
- v1 excludes: menu bar, shortcuts, focus mode, learning/translation modes, Web API, database
- Only genuine 404s are cached negatively, errors are never cached
- Prefer no lyrics over mismatched-duration lyrics
- Track identity includes URI kind (media vs track share IDs)
- Non-music items never touch the lyrics cache or network
- A line "errors surface as a retry state and re-attempt every 30s"
- Qt defaults windows to FullScreenPrimary; Primary and Auxiliary are mutually exclusive, so the all-desktops toggle must clear Primary. Native state is verified by readback, not assumed.
- Full-screen overlay requires accessory activation policy, not just collection-behavior flags; a Regular-policy app triggers a Space switch on activation. Window is unfocusable by design.
- Learning features are opt-in, toggleable layers. The default experience is always a simple synced-lyrics window; every layer off must equal the original core app.
- User-made syncs are not cache. They live in .user_syncs/ as plain .lrc, are consulted before cache and network, and nothing in the app or its docs may delete them — clearing .lyrics_cache/ must stay a safe reset.
- Tap timing = interpolated position (last poll + wall-clock since it landed) minus a reaction offset, clamped to >= 0 and >= the previous stamp. The UI thread never runs a subprocess to get a fresher position; the monitor stamps each poll instead.
- A sync is saved only when complete. Exiting early discards, and confirmation is inline (two-step control), never a modal — the window must never take focus or activate the app.
- A re-sync takes its lines from the sync it replaces, not a re-fetch: a completed pass stamps every non-blank plain line, so the stored lines ARE the song's lines. Re-syncing therefore works offline and after .lyrics_cache/ is cleared. LRCLIB's own timings are never offered for overwrite — only the user's.
- A sync pass is modal and user-driven: a fetch landing under it must not tear it down. The result is held and becomes where cancelling lands.
- Accessory activation policy is permanent and unconditional, applied before any window exists. It is no longer coupled to the all-desktops toggle, which now owns only collection behaviour and window level. There is no regular policy to fall back to, so nothing can bring the Dock icon back.
- One QMenu serves both the menu bar item and the window's right-click menu — two menus could drift apart, one cannot. Its structure is built once and never rebuilt; refresh only flips visibility, check marks and labels, so the native menu bar item never flickers. Checkable entries connect to triggered, not toggled: refresh calls setChecked on all of them.
- The menu bar item is the way back from a hidden window, so quit must be visible in every state and hiding must leave the monitor, loop and any sync pass running.
- QSettings location is injected into LyricsWindow, not global. QSettings.setDefaultFormat/setPath are process-wide and silently do nothing on macOS — trusting them meant tests writing into the real user's preferences.
- Tests must never reach the real Spotify. Entering a sync pass dispatches a seek-to-0 and a resume, so the Qt tests stub PlayerCommandTask/SeekTask/SpeakTask as well as the monitor thread; otherwise running the suite restarts whatever the developer is listening to.
- SESSION RULE: tests must never touch real user state, the network, or Spotify. Settings are injected; player commands, speech, and lyrics fetching are stubbed. Four escapes were found by their symptoms rather than by the suite — real QSettings writes, real player commands, a tray test that never ran, and a live LRCLIB fetch that aborted CI — so the seams are now backed by guards in tests/conftest.py: outbound sockets, subprocess, a bare LyricsProvider, and QSettings("lyrisync", "lyrisync") all refuse.
- A guard must record, not merely raise. Every escape happens on a worker thread, and the app catches broad exceptions there by design (a failed fetch is a retry state, not a crash), so an exception alone is swallowed exactly where it matters. Each block is recorded and an autouse fixture fails the test that caused it. The guards have tests of their own — an unrun guard is the tray test again.
- A QThread destroyed while it is still running is a qFatal: the process aborts (exit 134, "QThread: Destroyed while thread is still running") and names whichever test was on screen, which is how a shutdown bug came to look like a bug in the quit test. So _shutdown drains everything the window owns — monitor thread, then the worker pool — before anything of the window's is destroyed, and the Qt fixture forces any surviving thread down so a regression fails with a sentence instead of a signal.
- Shutdown's waits are bounded and honest. A worker that will not return in 3s (`say` can hold a line for a minute) is logged and left to the thread pool's own destructor, which is where it was always going to be dealt with; blocking quit on it would be worse than the warning.
- Legibility over an arbitrary background outranks the material. The scrim alpha is measured, not chosen by eye: the sung line must clear 4.5:1 with no blur behind it at all, so a material that fails to attach or renders pale costs depth and never readability.
- The vibrancy material is an NSVisualEffectView slid under the Qt content. The opacity gesture needs no plumbing: it rides on the NSWindow's alpha, which dims the material too.
- SUPERSEDES the pinned-dark material: the window follows the system appearance in both directions, live. Pinning dark was right only while the text was always white; now the palette inverts with the mode, so hudWindow in Aqua is the correct pale panel. The appearance is still set explicitly rather than left to inherit, for a new reason — the scrim painted on top comes from the palette this app resolved, and one answer must drive both or they disagree mid-transition.
- Following the system is Qt's colorScheme/colorSchemeChanged, not a pyobjc KVO observer or a distributed notification. The cocoa plugin already watches NSApp.effectiveAppearance and republishes it, so it costs no pyobjc and cannot disagree with Qt's own palette. Measured: the signal fires immediately on a real appearance change, and the app followed it mid-run with no relaunch (three screenshots dark, three light, one process).
- macOS's Auto transition is not a separate path. Flipping dark mode via System Events leaves AppleInterfaceStyleSwitchesAutomatically at 1 — measured — so the scheduled change and a manual one are the same effectiveAppearance change, and nothing in the code knows about sunset.
- Which backdrop is worst FLIPS with the mode, and missing that is how a light mode ships broken. White text on a dark scrim is worst over a WHITE page; dark text on a light scrim is worst over a BLACK one. Each palette is measured against the backdrop that suits it least: dark crosses 4.5:1 at alpha 147 and ships 150, light crosses at 131 and ships 134.
- Parity is pinned role by role, not just for the sung line. Every role that recedes in dark mode must recede no further in light mode, in each one's own worst case — four light colours (both accent blues, the idle control, the warning red) were swept until they satisfied it rather than picked by eye. Only the sung line carries 4.5:1; the parity test is what stops "meant to recede" becoming "gone" on one side only.
- Measured from real pixels, both modes, material rendering: dark reads 9.3:1 / 16.0:1 / 8.9:1 over a white document, a dark editor and a bright video; light reads 15.2:1 / 10.3:1 / 15.5:1. Floors without the material are 4.70:1 and 4.72:1.
- The screenshot harness needs two things that were wrong the first time and looked fine: an accessory-policy app cannot own a Space, so a showFullScreen backdrop never comes forward and every shot silently catches the desktop instead (all three captures were byte-identical); and the capture rect must come from the NSWindow frame converted out of Cocoa's bottom-left origin, because Qt's geometry disagreed with the screen by the menu bar.
- No appearance toggle. macOS already answers this question and a setting would be a second source of truth for it — the same argument as the login item's tick following the system.
- THE GOVERNING RULE for the album-colour tint: the artwork supplies a HUE and nothing else. Its own luminance and saturation are discarded and replaced with ours, per mode. The failure this prevents is the obvious implementation — sample a colour, paint with it — which works for three albums and then meets a neon cover or a near-white one.
- The tinted background is solved by BISECTION onto the untinted colour's relative luminance, not by holding HSL lightness. The two are not the same quantity and disagree badly across hues (pure yellow and pure blue sit at the same HSL lightness and nowhere near the same luminance), so pinning the wrong one would have moved the contrast floor by hue — the exact bug a hue-only tint exists to avoid. Measured: sweeping all 360 hues at full saturation moves the scrim's luminance by under 8% (that residue is 8-bit quantisation) and costs 0.03 of the floor — 4.70→4.67 dark, 4.72→4.69 light.
- Because luminance is pinned, character is free: sweeping tint saturation 0.60→1.00 moves the worst-case contrast by 0.01. So the saturations are high (0.85 dark, 0.95 light) rather than timid — the usual trade of character against legibility is simply not being made. Short of 1.00 only because full saturation pins a channel to 0 or 255 and reads as electric.
- Only the two backgrounds are tinted; every text colour keeps the value 12a measured. That is what lets the floor be re-CHECKED under tint rather than re-derived, and the parity work from 12a stays valid untouched.
- Measured with a deliberately hostile fully saturated cover, material rendering: dark 9.3:1 over a white page and 17.2:1 over a black one; light 15.2:1 and 9.7:1. Analytic floors with no material at all, swept across every hue: 4.67:1 and 4.69:1.
- The artwork line gets a try of its OWN nested inside the snapshot script's existing one. Appended to the same statement, a Spotify build that would not answer `artwork url` would fail the whole expression and take the six track fields with it — the app would show a running player and never find a song, for the sake of a colour. Nested, the cost is one missing line. artwork_url is deliberately not part of track_key: a cover arriving a poll later must not read as a different song.
- Extraction is a dominant-hue vote, not an average — averaging a cover gives mud (a red sleeve on black averages to dark maroon; a photograph averages to grey). Near-black, near-white and low-saturation pixels are discarded before voting, because nearly every sleeve is mostly dark and letting those count makes every album the same colour. A cover with no usable hue is a real answer: no tint, rather than a hue invented from noise. Confirmed live — the cover for "I'll Show You" is a black-and-white photograph, median saturation 0.005, and correctly produced no tint at all.
- The cache holds the DERIVED COLOUR, never the image: three integers of JSON per track against 100KB+ per cover, and nothing ever needs to look at one twice. "No usable hue" is cached like a definitive 404; a failed fetch and an image that will not decode are never cached, which is why decode_colour raises for one and returns None for the other rather than conflating them.
- Album colour is ALWAYS_VISIBLE, unlike the learning layers. Those hide because they cannot act (nothing to romanise without hangul); this one can always be answered and is a standing preference about the window, so appearing and vanishing with each track would hide it exactly when the user goes looking — before the music starts. Default off, like every layer.
- test_user_sync_safety's "only one module writes" check now permits artwork.py, and pays for it with a stronger claim: artwork.py may not so much as mention the user-sync directory. A module that learns to write has to argue for itself there first.
- Milestone 13 was a feel pass: no new behaviour, four changes to how the window reads. Lines rise as they change, the panel has an edge and a shadow, the album tint is restrained, and the type has a real hierarchy.
- Vertical motion is ONE signed property, not separate opacity and offset ones: `progress` runs -1 (gone, drifted up) through 0 (in place) to +1 (not yet arrived, below), with opacity = 1-|progress| and offset = progress x travel. They are not independent — a line half faded is half travelled — and one QPropertyAnimation per line change beats a parallel group of two.
- It is a QGraphicsEffect, not a moved widget. `_current_box` lives in a QVBoxLayout, so anything that moved it would be undone by the next layout pass and would ripple into the rows above and below. Drawing the source pixmap at an offset touches no geometry, which is why the rest of the window cannot feel it happening. boundingRectFor must grow by the travel or the moving block is clipped to its own box and reads as dissolving at the edge.
- The line change is 260ms per phase, extended EARLIER rather than finishing later: the arrival still settles exactly on the timestamp, it just starts moving 520ms before it instead of 200ms. Every constant derives from the one phase length so the swap point and the total window cannot drift apart from it. Sine rather than cubic easing — cubic's ends are steep enough that even 260ms reads as a flick — still In leaving and Out arriving, so the outgoing is fastest exactly where the incoming picks up and the two phases read as one movement. Travel went 7 to 10px: distance and duration are a pair, and a distance that read as a twitch at 100ms reads as too little at 260ms.
- A gap shorter than the choreography gets a QUICKER version of the same movement, not a truncated one: each phase takes at most half the gap. Both phases still fit before the timestamp and the arrival still lands ON it, at any tempo — a 400ms gap gets 200ms phases, a 120ms gap gets 60ms. The animation reads that per-transition duration rather than the nominal constant, or the clamp would be decorative and the movement would overrun the line it belongs to.
- CPU per line change grew with the duration, as expected and measured: 1.7ms for the text swap, 57.8ms for the fade, 92.7ms with the rise — against 34.1ms at the old 100ms pacing. That is 2.3% of one core at a line every four seconds, and 0.16% between lines.
- The anticipatory schedule stays authoritative and unchanged. The rise ENDS at the line's timestamp rather than starting there — motion completes on time. Eased both ways and differently: InCubic leaving (accelerates away, reads as departure), OutCubic arriving (decelerates onto its mark, reads as settling).
- QWidget::grab()/render() does NOT apply QGraphicsEffect — measured, after it produced nonsense readings. So an effect can never be verified through grab(); the reliable readback is tracing draw() itself. A real line change calls it 8 times per phase with the eased progress sequence, which is a stronger check than any screenshot.
- macOS's window server hands back a STALE frame on the first capture after a change, so frozen single frames of an animation are not trustworthy — three attempts at a filmstrip disagreed with each other. Static states screenshot fine; motion has to be measured, not photographed.
- Measured CPU per line change: 6.7ms for the text swap, ~26ms for the fade that already existed, ~1.3ms for the rise this added. At one line every four seconds that is 0.85% of one core, and the rise's own share is 0.03%.
- The hairline is ONE DEVICE pixel (1.0 / devicePixelRatioF), not one logical pixel: at 2x those differ by a factor of two and a two-pixel line is a border rather than an edge. Inset by half its own width so it lands inside the fill — straddling the boundary would put half the stroke outside the material's mask and read as a second, softer edge beside the first. Palette-owned, and deliberately never tinted by the album: a coloured hairline reads as a border.
- The shadow is the native NSWindow one (setHasShadow_), not a painted one: macOS derives the shape from the alpha channel so it follows the rounded corners for free, sits outside the window bounds where a painted one would have to eat into the panel, and costs the compositor nothing per frame. It is CACHED, so resize must call invalidateShadow or the old silhouette stays. Verified it survives the opacity gesture — at alphaValue 0.5 hasShadow is still true.
- The tint is specified as CHROMA of the finished panel (0-255 channel spread, after the background's alpha), not as HSL saturation. Diagnosed, not guessed: at 0.22 saturation the light tint moved the scrim by 3/255 — LESS than the palette's own built-in blue cast — so album colour looked switched off in light mode however strong the cover. The cause is that saturation collapses at both ends of the lightness range: the light scrim at L=0.973 can only reach 14/255 chroma even at S=1.0, while the dark scrim at L=0.067 gets 34/255 from the same number. One saturation therefore meant 2.4x more colour in dark than light. Stated as chroma the constant means the same thing in both modes.
- The saturation that yields a wanted chroma is found by BISECTING on saturation against the chroma actually achieved — not by inverting HSL's closed form. The closed form answers a different question (chroma at some lightness), and pinning the luminance then moves the lightness by wildly different amounts per hue. Feeding that back as a correction does not converge, it OSCILLATES: yellow alternated between chroma 204 and chroma 2 on successive rounds, and stopping after two landed on whichever the parity chose — which is how a yellow cover came out less coloured than no cover at all. Chroma rises monotonically with saturation at fixed luminance, so bisection converges and a hue that cannot reach the target settles for its most.
- Light mode carries genuinely less tint than dark, and it is the gamut, not a tuning failure. At the light panel's luminance 0.93 the hues that carry little luminance of their own (blues, magentas, reds) are nearly white — buying their colour costs brightness the pinned luminance will not give up. Delivered: dark 10.0-14.1 (median 13.5), light 4.7-12.1 (median 8.4). Relaxing the luminance was measured rather than assumed: a 5% drop buys the worst hue only 4.7 to 7.9 chroma and leaves the floor at 4.52, with none of the rounding headroom the rest of the palette keeps. So luminance stays pinned.
- Every hue must beat the UNTINTED panel's own chroma, in both modes. That is the test that would have caught the original bug, and it is the one that caught the oscillation too.
- CONTRAST HEADROOM IS NOT AESTHETIC HEADROOM. 12b set tint saturation to 0.85/0.95 because measurement showed saturation was nearly free; the reasoning was sound and the conclusion was wrong. What the floor permits and what looks like a pane of glass are different questions, and a near-fully-saturated wash answers only the first. Now 0.18/0.22, set by eye at the point where the colour is felt rather than noticed, with the floor re-checked afterwards rather than used to justify the value (4.68 dark, 4.69 light — unchanged).
- Qt stylesheets have no letter-spacing property, so tracking is the one type setting that cannot live with the others. It goes on via QFont, with the font read back AFTER the stylesheet has been applied and polished — measured that size and weight still come from the stylesheet afterwards, so typography.py stays the single source and this only adds what the stylesheet cannot say. Only the sung line is tracked; tightening body-size type costs legibility and buys nothing.
- The type hierarchy is 20/700 against 13/400 — a 1.54x size ratio and three weight steps, where it was 18/600 against 14/400 (1.29x and one step). At the old separation the eye had to read the window to find the current line. The floor grew 161 to 183 as a result, so the default window height went 170 to 200: a first run should open at a shape it chose, not at the floor it was clamped to.
- A test may not patch `window._pool` — it is QThreadPool.globalInstance(), a process-wide singleton, so assigning to its start() leaks into every test that runs afterwards (it broke three shutdown tests two files later). Record what a window starts with a recording subclass of the task instead.
- Blur and window translucency are mutually exclusive: macOS renders the behind-window blur only while alphaValue is exactly 1, and dimming either native view instead of the window does not save it. So the window starts fully opaque and dimming is understood as spending the frost to see through. Verified by screenshot, not by API docs, which say none of this.
- Screenshots are the readback for anything the compositor draws. _material is not None only proves the view attached; whether it blurs is a question about pixels, so the check is a capture over a text-heavy backdrop — sharp glyphs inside the window mean no blur however healthy the readback looks.
- typography.py owns the type scale and geometry.py imports it, so the height floor can never describe a type scale the stylesheet has moved on from.
- No colour emoji in the window. 🔊 renders in colour whatever is asked of it and macOS has no monochrome speaker glyph (U+1F56A and friends are tofu), so the speak button is ♬; 🎤 takes U+FE0E and goes monochrome.
- SUPERSEDES the line above for the speak button: the native answer is SF Symbols, not a hunt for a Unicode character that happens to render monochrome. `text.bubble` via NSImage.imageWithSystemSymbolName, tinted here because a template image carries its shape in the alpha channel and takes its colour from us. ♬ stays as the fallback for when symbols cannot be had (off macOS, no pyobjc, symbol missing) — symbols.py returns None and the button keeps the text it was built with, which is what lets the suite stay headless. Rendered per scale at the screen's device pixel ratio: an SF Symbol is drawn for the size it is asked for, and a 1x glyph stretched to 2x is visibly soft.
- One source for control colours: window.py owns _CONTROL_IDLE/_HOVER/_ENGAGED, the stylesheet paints text with them and symbols.py tints the icon with them, so the glyph and the icon that replaced it cannot describe different states.
- Packaged with PyInstaller, not py2app: PySide6 and pyobjc are both covered by hooks PyInstaller maintains upstream, where py2app needs hand-written recipes for the same bundle. `make app` is the whole build — icon, freeze, ad-hoc signature.
- The bundle identifier IS the settings contract: com.lyrisync.lyrisync is what QSettings("lyrisync", "lyrisync") already resolves to, so the bundled app and a terminal run share one plist. Verified by launching both at once and reading the window geometry back — same position, same size, same file.
- LSUIElement in Info.plist as well as apply_accessory_policy() at runtime. The runtime call is what the code guarantees; the plist key is what stops macOS showing a Dock icon for the instant before it runs.
- NSAppleEventsUsageDescription is load-bearing, not paperwork: without it macOS refuses the AppleScript calls silently and the app looks broken — window up, menu bar item present, never finds a song.
- Open at Login uses SMAppService.mainApp, not a LaunchAgent plist, because the menu entry has to show what the system thinks and only SMAppService can answer that: a plist stays exactly as written after the user disables the item in System Settings, so a menu built on it would keep claiming the app starts at login when it no longer does. The cost is macOS 13 (the app's floor is 11); below that the entry is not offered, which beats a fallback that cannot describe itself honestly on the very systems it would serve.
- The login item entry is never drawn from the stored preference. The setting records what the user asked for; status() is re-read at startup and on every menu opening, and the tick follows macOS. They are only ever compared to log the disagreement.
- REQUIRES_APPROVAL is not enabled. Registration can return no error and still not start the app at login, so set_enabled re-reads the status instead of trusting its own return, reports failure, and the entry stays unticked with a label naming System Settings — an unticked box that explains itself beats a ticked one that is wrong until next login.
- Measured, not assumed: a freshly built bundle reports NOT_FOUND (3) before it has ever been registered, registers cleanly under an ad-hoc signature with no approval step, and reports NOT_REGISTERED (0) after being switched off. So NOT_FOUND is an ordinary "off" and the entry is still offered from it. Verified by a throwaway probe built into a scratch bundle, registered and unregistered in one run, then reverted.
- Every native login-item call goes through login_item._main_app_service(), one door, so tests have one seam to block. A stray call would leave a real login item on whoever ran the suite.
- Bundle building stays out of CI. The artefact is macOS-only and what matters about it (menu bar icon, no Dock icon, the Automation prompt) can only be accepted by a person, so a green tick would be claiming more than it checked.
- No test is macOS-only. Everything native is guarded off-cocoa in the code and asserted structurally, so the whole suite runs headless on the offscreen platform. CI must apt-get PySide6's system libraries (libegl1, libgl1, libxkbcommon-x11-0, ...) — the wheel imports fine without them and only fails at load with "libEGL.so.1: cannot open shared object file", which pytest.importorskip does NOT skip by default (it is an ImportError, not a ModuleNotFoundError).
- The global hotkey is Carbon's RegisterEventHotKey, not a CGEventTap or an NSEvent global monitor. Those two read every keystroke on the machine, so macOS puts them behind an Accessibility prompt the user has to leave the app to answer; the event manager matches one combination itself and calls back only when it fires. Deprecated, but nothing replaced it, and this is what every menu bar utility with a shortcut and no Accessibility prompt is doing.
- pyobjc has no Carbon bindings, so it is ctypes — measured, not assumed: RegisterEventHotKey/InstallEventHandler/GetApplicationEventTarget all resolve, registration returns noErr with no prompt, and the one missing symbol (NewEventHandlerUPP) is a 64-bit no-op that returned its argument, so the ctypes callback IS the UPP. Verified again in the real app: "global hotkey ⇧⌘L registered" under the accessory policy, released on quit.
- Every native hotkey call goes through hotkey._carbon(), one door, same as login_item. A stray registration in the suite takes ⇧⌘L from whoever is running it, for as long as the process lives. Out-params go through ctypes.pointer, not byref, so the door can be faked and the register/press/release sequence tested for real.
- RegisterEventHotKey is NOT exclusive across apps — measured, and it corrected the code: two LyriSync processes both claimed ⇧⌘L and both got noErr, with macOS deciding between them per press. eventHotKeyExistsErr (-9878) comes back only when the SAME process already holds the combination. So a refusal is never "another app owns it", and neither the log line nor the README may say it is; the honest message names the OSStatus and points at the menu bar item.
- The hotkey drives _set_lyrics_visible — the menu entry's own setter — so there is one piece of state and the tick matches the window whichever was used. It is deliberately NOT shown on that menu entry: a QAction shortcut would be a second mechanism firing one action, and a label printing ⇧⌘L while another app owned the combination would be the login-item failure again, an entry claiming something untrue. The README carries the keys; the log says whether they landed.
- The hotkey is ⇧⌘J, moved from ⇧⌘L when that collided with something the user already runs. The move was one constant and its label, which is the argument for keeping it in one place. Key codes are verified against the live layout rather than read off a header: CGEventKeyboardGetUnicodeString on an event built from 0x26 answers "j" — and building a CGEvent needs no Accessibility permission, only posting one does.
- The monitor's stop is a threading.Event set once and never cleared, not a flag run() raises on entry. The old shape lost any stop() that landed between starting the thread and the thread body beginning — found while building the hotkey, not by the suite: it showed up as a 3s stall in test_visibility_survives_the_shutdown_save (every run) and an intermittent "monitor thread outlived _shutdown" in teardown, which is one bounded wait away from the qFatal. The remaining poll interval is now waited on rather than slept through, so quitting does not first sit out a poll: a real run quits in 0.3s and the suite went 4.2s → 1.3s.
- Releasing the hotkey is the FIRST thing _shutdown does. It is the only thing left that can still call in — Carbon holds a pointer to a callback that toggles a window being torn down. Unregister is idempotent (shutdown is reached more than once) and the ctypes callback object is dropped only after the handler is removed, because until then C holds a pointer into it.

- The line change played TWICE because the choreography (520ms) outgrew the poll interval (300ms) in 13.1, so a poll lands inside almost every change. Two separate causes, both needed fixing: the poll re-armed both timers from what was LEFT of the gap (a smaller eta, hence a hurried second run), and — the visible half — `_on_position_update` read the predicted swap's one-line lead over the view model as a missed prediction and re-rendered the line being left. Reproduced deterministically before fixing: the indices put on screen were [1, 0] where they should read [1].
- Dedupe is by TARGET LINE INDEX, the same shape as the view model's track identity: an announcement of what is already showing is not news. It is two questions, not one — `may_arm(target)` stays true until the movement begins, so an ordinary poll keeps re-deriving the schedule from a fresh position and a seek is still picked up within one poll; `begin(target)` is claimed by the fade-out, the moment the change stops being scheduled and starts happening, and refuses every later trigger for that line.
- Being ahead of the view model needs a BOUND, not just an owner. Suppressing the snap whenever the screen leads by one line would leave the window sitting on a line the song has left after a seek backwards into the middle of the current one — it would wait for a timestamp half a verse away. So `leads()` also asks whether the player is still within the choreography plus one poll interval of that timestamp; further than that is the world moving, and it snaps.
- SUPERSEDES "the hairline is deliberately never tinted by the album". The panel has no gamut left — its luminance is pinned by the 4.5:1 promise, and in light mode buying colour would cost brightness the floor will not give up. The hairline has no text on it, so it has no contrast obligation, and that is where the album colour now lives: the panel keeps its restrained wash and the edge carries the hue at ~4x. The old objection was that a coloured hairline reads as a border; measured against real covers in both modes it does not, because it is still one device pixel and still inset.
- Freed of the luminance pin, the hairline pins HSL LIGHTNESS instead, and that buys the one thing the panel can never have: at a fixed lightness an HSL colour's chroma is exactly saturation x (1 - |2L - 1|), with NO HUE TERM. So the edge is solved by arithmetic rather than bisection and delivers 46.2 units for all 360 hues in dark and 45.7 in light — identical across hues, and the same in both modes — where the panel bisects per hue and still lands 10.0-14.1 dark, 4.7-12.1 light. Stated as delivered chroma (after the edge's own alpha), the same convention as the panel, so the two numbers can be compared.
- What FIXES the two lightnesses is that a coloured line is not automatically an edge: it must stay lighter than the dark panel and darker than the pale one, for every hue, over the backdrop that leaves the panel closest to it. The binding cases are blue in dark mode and yellow in light — the hues furthest from their own panel in luminance — and they put the values at 0.72 and 0.30 (worst separation +0.0386 and +0.0053). Alpha (110/105) is a free knob against saturation for the same delivered chroma; it is what lets a strongly coloured edge not be a strongly saturated one.
- Contrast floors re-checked, not re-derived: 4.677 dark and 4.692 light swept over all 360 hues, identical to 13.1's. Nothing else could have happened — the tint touches only `border`, and the test that says so is the one that used to say only scrim and solid moved. Measured from real pixels with the material rendering, over each mode's worst backdrop: 11.4-11.6:1 dark and 11.9-12.0:1 light, with the tint moving it by under 0.3 in the safe direction.
- The window shadow is NOT tinted, and it is not a judgement call: NSWindow exposes hasShadow/invalidateShadow/setShadowStyle_ and nothing about colour (the shadow is drawn by the window server from the alpha channel; every colour-adjacent symbol is private). Tinting it would mean giving up the native shadow for a painted one, which is exactly the trade 13 refused — a painted shadow sits inside the window's bounds and costs the compositor per frame.
- A screenshot harness must PUMP the event loop, never sleep in it. `time.sleep` inside the slot doing the capturing blocks Qt from repainting, so every capture comes back byte-identical and the whole run looks like the stale-frame problem — twelve shots, six distinct pairs, all wrong. Spin processEvents in a loop instead, and keep throwing the first capture away.
- The tinted edge and the tinted panel ride ONE cross-fade mix. Two animations of the same tint could only drift apart, and an edge that changed colour before its panel would read as a flicker at the rim.

- The bundle's version comes from importlib.metadata.version("lyrisync") — the INSTALLED distribution, not a re-read of pyproject.toml and never a literal — because the installed package is what PyInstaller freezes. Reading the file would describe the source tree, which is the same thing right up until it is not. - LYRICS FAILURES NOW SAY WHY, ONE CLICK AWAY. The provider knew whether it was a 503, a timeout, an unreachable socket or an unreadable body, and which of the three fallback attempts it happened on, and threw all of it away at `except LyricsError:`. - WHAT WAS FOUND, BEFORE ANYTHING WAS FIXED. Over the scrim with the material contributing nothing, the sung line clears 4.70:1 (dark) and 4.72:1 (light) and NOTHING ELSE CLEARS 4.5 AT ALL: plain 3.76/3.78, pronunciation 3.12/3.24, context 2.76/2.94, header 2.48/2.48, progress 2.13/2.28, the idle control 2.12/2.17. That is the hierarchy working exactly as designed and the wrong answer to somebody who has asked the system for more contrast.

- DROPPING THE MATERIAL IS WORTH MORE THAN ANY RECOLOURING. On an opaque panel the sung line goes from 4.70:1 to 17.93:1 in dark and 4.72:1 to 16.89:1 in light, and every text role but two clears 4.5 with nothing else done. So Increase Contrast is a SHORT list of overrides, not a third pair of palettes: dark lifts control_idle 105->120, scrollbar 70->90, sync_text_off 60->90 and the hairline 30->90; light lifts header 140->155, control_idle 120->155, scrollbar 70->124, sync_text_off 60->124, tap_text_off 110->124, the hairline 38->112, and attempt_text from alpha 245 to 255 — the one role with no alpha left to give, at 4.25:1 over its own hovered amber fill and 4.56:1 at full opacity.
- Two floors, because two kinds of thing are being lifted: 4.5:1 for anything read to follow a song, 3:1 for the marks (scrollbar, hairline) and the labels on switched-off controls, which WCAG exempts outright and which this holds anyway. "PAUSED" on the tap bar is a disabled control and is still the one word explaining why tapping does nothing.
- THE ALBUM TINT'S HAIRLINE IS NOT LIFTED, and that is a decision rather than an oversight. Measured over the opaque panel it is 2.02:1 (dark) and 1.62:1 (light) at its worst hue, and reaching 3:1 needs alpha 163 and 218 — a nearly opaque line, which would end the hue-only design that BORDER_CHROMA exists to hold. Nothing is read against the hairline; the panel and every word on it clear their floors with the tint on, which is checked over all 72 hues.
- REDUCE MOTION TAKES THE TRAVEL AND LEAVES THE FADE, and `progress` being ONE signed number is what makes that a one-line change: the opacity and the offset are the same journey, so removing the rise is setting its length to zero. The choreography, the phase length and the arrival on the timestamp are all untouched — what was a rise becomes a cross-fade of exactly the same duration.
- The flight goes entirely, rather than becoming a quick one. It is movement in every dimension it has — position, scale and opacity — so there is nothing left to keep once the movement is taken out, and a fade in place would be answering a question nobody asked. Any flight in the air gives back everything it borrowed first. The travel to a remembered position goes the same way: the window still arrives, it simply does not travel.
- The tint cross-fade, the notification yield and the learned-position glow are all LEFT ALONE. They are fades, which is what Reduce Motion asks to be given instead of movement, not movement to be removed.
- THE SETTINGS COULD NOT BE TOGGLED FROM HERE, and the session says so rather than claiming otherwise. com.apple.universalaccess is TCC-protected: `defaults write` answers "Could not write domain com.apple.universalaccess; exiting" without Full Disk Access. What WAS verified live is the observation path — an observer registered on NSWorkspace's notification centre received NSWorkspaceAccessibilityDisplayOptionsDidChangeNotification when it was posted — and every response to an option is tested by handing the window the option. The real switches are manual-verify, which is where they have to be.
- A MAC WITH NO SPOTIFY ON IT DID NOT WORK, and the reason is one line above where anyone would look. `if application "Spotify" is not running then return "not_running"` is the snapshot script's first line and reads like the answer; everything below it is Spotify's OWN terminology, and AppleScript resolves terminology at COMPILE time out of the application bundle. With no bundle the script never runs at all — measured, by asking with a name that is not installed: `141:146: syntax error: Expected “,” but found identifier. (-2741)`.
- What that produced: poll_once swallowed the error, NO state callback ever fired, and osascript was spawned three times a second forever for a script that could not compile. The window happened to look right — "Spotify is not playing" is its initial state — which is exactly why nothing had ever noticed.
- The fix is a second, dictionary-free script (`running` is a property of AppleScript's own generic application class, so it compiles anywhere), asked only when the snapshot fails, and REMEMBERED. Measured: a snapshot costs 184 ms where Spotify exists; the probe costs 37 ms there and 182 ms where the application is absent, because LaunchServices goes looking for something that is not there. Without the memory a Mac with no Spotify pays for both on every poll; with it, it settles into the probe alone — which is also what notices Spotify being installed later, since it is asked again every time.
- `run script` was measured as the alternative — one call always, with the terminology-dependent half deferred to runtime — and rejected at 199.9 ms against 183.9 ms median, 9% of a 300 ms poll interval paid by every Mac to fix the case of the Mac that has no Spotify.
- poll_once now LOGS the failure it used to swallow. At debug, not warning: a genuinely transient failure happens, and one line three times a second is a stream rather than a diagnostic.

- Milestone 17 (a compact layout, and a command that puts the window under the menu bar).
- THE LAYOUT IS ONE MORE OPT-IN LAYER and is held to the layers rule, which for a LAYOUT means more than hiding rows: off is the window the app has always had, at the height it was last left at, with no reveal, no pointer watch, and no graphics effect on any control. The rows either side of the sung line are not written to at all in compact — "off removes the work" — and the opacity effects are DESTROYED rather than left at 1.0, which is the same argument Reduce Transparency already made about a hidden effect view still being one.
- THE FLOOR IS DERIVED, like the five-row one, and drops two things with the three rows. It drops the 120 floor, because 120 is where five rows stop fitting and that is not a fact about two. And it drops CURRENT_SPACING, the air above and below the sung line, because that air exists to stop three lyric rows reading as an evenly spaced list with one of them in bold, and with no neighbours there is nothing to separate from. 79px against 183 at scale 1.0, 51 against 120 at the narrowest window the app has.

- _MIN_SIZE's height was a SECOND COPY of the five-row floor (QSize(260, 120) against _MIN_HEIGHT_FLOOR = 120) and had to go, or a restored strip would be clamped up to a shape nobody chose in the window between setMinimumSize and the first _apply_layout_margins. It is now min_window_height(_MIN_SCALE, compact=True), and _MIN_SCALE = 0.65 replaced the same literal in two places, one of which is the resize floor computing the scale a drag is ABOUT to land on.
- EACH LAYOUT KEEPS THE HEIGHT IT WAS LAST LEFT AT (window/full_height, window/compact_height). Not tidiness: a sync pass borrows the full layout without being asked to, and Qt does not shrink a window when a minimum drops, so without this every sync pass would have left the strip permanently 150px taller than the user put it.
- FOUND BY SCREENSHOT, and it is the third time this rule has earned its place. A long line WRAPS, the full layout's floor leaves room for the second row, and a strip has no such room by construction: the second row landed halfway on top of the romanisation, cut through the middle. Every number was correct — the window was at its floor and the floor was right. Compact now does not wrap and elides instead, measuring against the window and its gutters rather than the label's own width, because the elision runs before the layout that would produce one. The unelided line is kept, or a resize would eat it a word at a time.
- THE HOVER REVEAL WAS WRITTEN AS enterEvent AND leaveEvent, and it passed, and it was wrong. Driving the real pointer onto the real window with the app BACKGROUNDED — accessory policy, WindowDoesNotAcceptFocus, Finder in front, which is the only state this app is ever in — the window heard nothing: hovered stayed False with the cursor provably inside its frame. Qt installs its tracking area NSTrackingActiveInActiveApp, so an app that never activates has no hover events to miss. The test suite could not have caught it: the offscreen platform has no pointer.
- What still answers is the pointer's POSITION, which is a screen coordinate and belongs to nobody. So this is the second thing in the app that genuinely has to ask, on a 100ms timer running only while the layout is in force and the window is showing. Measured at 0.8us a poll, 0.0008% of a core at that rate; the interval is the whole of the latency and 100ms is already under the hand's arrival.
- Asking the pointer also deleted a bug the event version would have had anyway: Qt sends the window a Leave the moment the pointer moves onto one of the window's OWN controls, and underMouse() is false for the same reason. A frame contains its children, so the question stopped needing an answer.
- A CONTROL FADED TO ZERO IS TAKEN OFF THE WINDOW, not left invisible: a widget at zero opacity is still a widget under the pointer, and an invisible thing that can be clicked is worse than either state it is between.
- The fade was verified by SCREEN CAPTURE at five levels, because grab()/render() does not apply a QGraphicsEffect and could only ever have agreed with itself. Darkest pixel of the loop button over the light panel: 132, 157, 182, 207, 232 at 1.0, 0.75, 0.5, 0.25, 0.0. A clean ramp to the panel's own colour, and gone at the end.
- A SYNC PASS TAKES THE FULL LAYOUT BACK and echo practice does NOT. The pass needs the line before, the line after, a status row and a tap bar across the bottom; a strip has room for one of those and the bar alone would BE the window. Echo is the opposite case: one line repeated is the compact layout at its best, and the loop engages and releases many times a song, so a fallback keyed on it would be a window resizing itself every few seconds. Instead the reveal is HELD OPEN while the attempt is waiting — that phase pauses the song and the done button is the only way out of it, and a prompt nobody can see is not a prompt.
- The setting and the layout are two variables on purpose (`_compact` and `_compact_applied`), and the menu's tick follows the first. A pass borrowing the layout is not the user changing their mind.
- THE COMPACT GUTTER RESERVES TWO CONTROLS A SIDE, not one: a strip has no top-right corner, so the loop and the speak button come down onto the centre line and sit side by side. The same margin on both sides even though only the right one carries two, because the sung line is centred and an asymmetric gutter would centre it in what is left of the window rather than in the window. 72px a side at scale 1.0 against the full layout's 40.
- DOCK TO TOP IS A COMMAND, not a snap. Nothing is magnetic, no edge attracts, and the window is as draggable the instant after as the instant before. It exists because "centred under the menu bar" is tedious to hit by hand and obvious to want, especially with the strip.
- Centred on the SCREEN rather than on the available area, which are not the same thing once the Dock is on the left or the right: the menu bar spans the screen and the notch is centred on it, so centring on anything else would put the window off-centre from the thing it is lining up with. Flush, with no gap of its own, because "just below the menu bar" is a position and a gap would be a number set by eye.
- THE SAFE AREA IS A FLOOR ON THE AVAILABLE AREA, never a replacement, and it is worth writing down that it usually changes NOTHING. Measured live on this 14" MacBook Pro: screen 1710x1107, available top 34, safe-area top 33 — with the menu bar showing, macOS has already reserved the whole band the notch sits in and the available area is the answer. The one case they come apart is the one people actually use: "Automatically hide and show the menu bar" gives the whole screen back and leaves the notch exactly where it was, and without the inset the window would dock underneath it.
- It is read off the window's OWN NSScreen through the _nswindow() door that already exists, rather than matching Qt screens to NSScreens by frame. That version was written first and thrown away: it needed the Cocoa-to-Qt origin flip, a match that is ambiguous on mirrored displays, and a whole new native door to guard — all to answer a question the window can ask about itself.
- A DOCK IS LEARNED LIKE THE END OF A DRAG. With per-app position memory on, a dock that was not recorded would be undone by the very next app switch, and docking is the user saying where the window goes, which is exactly what a drag says. _learn_position now takes an optional position, because the travel takes a phase length and neither the save nor the learn may record a waypoint.
- A window away at the menu bar is docked by moving where the FLIGHT will put it back, not by moving the window: the flight is holding the real position and would hand the old one straight back on landing. Same lesson as _land's ordering, one level up.
- sync_bar_gap and the gap between two compact controls were the same question asked twice, so control_gap is now the one definition and sync_bar_gap returns it.

- Milestone 18 (fitting the strip to the song, and the measurement that changed what the feature is).
- THE OBVIOUS IMPLEMENTATION IS IMPOSSIBLE, and it is a property of this app rather than a bug in it. The type scale follows the window's width, so the room for a line and the line itself grow at exactly the same rate and the window's width CANCELS: available/text = (w - 2*gutter(w/460)) / (T*w/460) = (460 - 144)/T. A line wider than 316pt at scale 1.0 fits at NO width, and one narrower fits at every width. Measured over 14 real songs from the cache at every width from 260 to 3000: 13 of them never fit, and the median song's widest line is 466pt. "Make the window wide enough" has no answer.
- So the TYPE SCALE IS HELD while the strip sizes itself, and the width the user chose stops being a width and becomes a type size: it still sets the scale, the song sets the width, and dragging an edge hands both back at once. The milestone's own wording asked for this without knowing it — "measure the widest line at the current type scale" is only meaningful if the scale stays put.
- Holding the scale is ALSO why height adaptation needed no code and could stay out of scope. The height floor comes off the same scale, so a width that moves under a held scale leaves the floor, and the height, exactly where they were.
- WHAT IT PRODUCES, measured against those 14 songs with the scale at 1.0: narrowest song 267pt of line and a 411pt window, median 466 and 610, widest 695 and 839. Three shot on the real window at each song's widest line: 412, 561 and 839, each showing that line whole.
- THE CAP IS HALF THE SCREEN, past which a floating strip stops reading as an overlay on somebody's work and starts reading as a window over it. Checked against 776 lines from the same 14 songs: the widest needs 839 and the cap on the 1710pt screen this was measured on is 855, so nothing in the corpus is clipped; on a 1440pt screen the cap is 720 and 4 of the 14 are, which is the cap working rather than failing. A screen-relative bound means a smaller screen gets a proportionally smaller strip rather than the same strip taking more of it.
- A DOCKED WINDOW IS RE-DOCKED RATHER THAN CENTRE-ANCHORED, and it is recognised by being exactly where docking put it rather than by a flag somebody has to remember to clear. The two rules almost agree already, since docking centres on the screen and centre-anchoring keeps the centre, but the two floor divisions disagree by a pixel when the widths differ in parity, and a window that wandered a pixel per song would be off centre by the end of an album. Verified live: docked at 839 wide the window sits at x=435, at 412 wide at x=649, both exactly the screen-centred value and both at y=34, clear of the 33pt notch.
- The motion was MEASURED RATHER THAN PHOTOGRAPHED, as the rule says: sampling the geometry at every tenth of the travel, the centre drifts by at most one pixel, which is integer geometry rounding and nothing else.
- One animation over the whole GEOMETRY rather than a move and a resize handed to each other: the position is a function of the width here, and two animations would have to agree about it frame by frame.
- LANDED, NOT ABANDONED. Anything that takes the window's position over for its own reasons — the travel to a remembered position, the flight to the menu bar, the save at shutdown — finishes a resize in flight instead of stopping it. A window left at a waypoint would stay there, because nothing would ask again; the flight already made this argument about position and it is the same one about width.
- _relayout exists because a HIDDEN widget defers its resize event until it is shown, so a strip resized while away would come back laid out for the width it used to have. Found by a test asserting the type scale after the feature was switched off: 0.87 where 1.09 was wanted, because the resize event that would have recomputed it had never been delivered.
- FOUND BY LOOKING, and it was the harness rather than the app: the first shot of the widest song was an empty 839pt strip. The take had seeked to 20s and that song's first line is at 29.35s. Worth writing down because the screenshot was RIGHT and looked like a bug, which is the opposite of the usual failure and just as expensive.
- The fit refuses while the window is hidden or in flight, and the show re-fits before the flight takes off. An album played hidden costs nothing, and the flight is holding the window's real geometry and would hand the old width back on landing.
- scale_for, BASE_WIDTH, MIN_WIDTH and MIN_SCALE moved from window.py into geometry.py, which is where a rule about how a window's width becomes a type scale belongs. It also lets the impossibility above be a PURE test rather than one that needs Qt, which is the only reason it is a test at all.
- The one setting in this app that defaults ON, and it can be: it is reachable only from inside the compact layout, which is itself opt-in and default off, so the plain synced-lyrics window is exactly what it always was. The menu entry follows compact for the same reason every other gated entry follows what it needs.
- A drag on an edge turns it off at the START of the drag rather than at the end, so the drag behaves exactly as it does with the feature off: the type scale follows the edge live instead of being pinned for the length of the gesture and jumping when it is let go. A drag on the window itself is not a resize and changes nothing.
- _remember_size declines to record the WIDTH while the song is choosing it. That slot is the user's own width, it is what the scale is pinned to, and overwriting it with a fitted one would let the type drift a song at a time towards whatever the longest line happened to be.

- Milestone 19 was an ENERGY session: the app's twelve-hour energy impact sat beside Claude Desktop's and about triple Spotify's, which is not a thing a lyrics window should cost. No feature changed. The finding was that almost none of what it cost was the work.
- MEASURED FIRST, and the attribution is the whole milestone. One snapshot poll cost 58.8ms of CPU, of which 2.9ms was ours and 55.9ms was the `osascript` CHILD. At 3.3 polls a second that is 19.6% of one core, against 2.3% for a line change at a line every four seconds, 0.035% for the notification yield's poll and 0.0008% for the compact hover poll. Everything the sessions before had tuned was rounding error beside the thing nobody had priced.
- And it did not land only on us. Sampling every process on the machine across a polling window against an idle control, four daemons woke on every poll and were flat without one: loginwindow 11.0%, tccd 8.6%, launchservicesd 7.8%, runningboardd 2.7% — about 30 percentage points of one core spent carrying a process launch, three times a second, forever. That is the cost of asking, not of the answer.
- SO THE CARRIER CHANGED, NOT THE QUESTION. The identical script sent through NSAppleScript in this process: 58.8ms → 5.5ms of CPU and 200ms → 133ms of wall. Compiled ONCE and kept, which is the difference between 5.5ms and 24.3ms; compiling per call is 19ms of the 24. The subprocess was never the question, it was fork, exec, LaunchServices, TCC and the AppleScript framework being loaded and thrown away.
- ONE EXECUTION AT A TIME, and the lock is measured rather than defensive: three threads executing one compiled script concurrently took 6.8s per execution against 0.13s serialised, with no errors and no wrong answers. Fifty times slower for the privilege. The monitor's thread and the pool's seek/pause/resume are the two callers and they do collide.
- THE ONE THING THAT NEARLY SHIPPED A DIALOGUE. A `tell application "Spotify"` block needs the dictionary at compile time, which is why a Mac with no Spotify could never compile it — that was known, and the old code paid 182ms for a syntax error inside a throwaway osascript. Compiled in THIS process it does not fail: macOS puts up its "Where is Spotify?" application chooser, in front of the user, and blocks the thread. Measured by compiling against an application name that is not installed: still blocked after five minutes, with a file panel on screen owned by the app.
- WORSE, the dictionary-free probe kept for exactly that case does the same thing. `if application "X" is not running`, which compiles anywhere, blocks identically — what cannot be resolved is the application, not its vocabulary. There is no AppleScript that is safe to ask about an application that might not be there.
- So the gate stopped being a script. `spotify_running` is now NSRunningApplication against the bundle identifier: 0.017ms of CPU against 25.7ms for the AppleScript probe, no Apple event, no LaunchServices search, no permission — and it is asked BEFORE anything is compiled or sent rather than after a failure. An application that is running is one whose bundle is on disk, so the chooser has nothing to ask about. The `_no_spotify_installed` memory and `_RUNNING_SCRIPT` both went: they existed because the probe was expensive, and it is not any more.
- THE QUERY'S BOUND HAD TO BE PUT BACK, in the script. subprocess.run's timeout used to be it; NSAppleScript sends with the Apple Event Manager's default, which is about a minute, and a minute is one wedged Spotify away from a monitor thread outliving shutdown's three-second wait — a QThread destroyed while running, which aborts the process. `with timeout of 2 seconds` is AppleScript's own, needs no dictionary, and is the same two seconds.
- SPOTIFY ANNOUNCES ITSELF, and the payload was read off the wire rather than off a blog post. `com.spotify.client.PlaybackStateChanged` carries Album, Album Artist, Artist, Disc Number, Duration, Has Artwork, Name, Play Count, Playback Position, Player State, Popularity, Track ID (the full URI, so the kind is in there) and Track Number.
- Each case was DRIVEN and timed: pause 0.50s, play 0.11s, next track 0.14s, a track ending on its own 0.5s (position 0.008), Spotify quitting 0.89s ("Stopped", no Track ID), Spotify launching 0.67s ("Stopped" then "Paused" with the track). The case with no notifications in it announces its own beginning and its own end.
- AND A SEEK ANNOUNCES NOTHING. Driven twice from AppleScript and once by `previous track` restarting the current song: nothing arrived, on any occasion. That is the entire remaining job of the poll loop, and it is why one survives at all.
- Registering with name=None to watch everything receives NOTHING on a modern macOS: 32 seconds of driving Spotify through eight commands delivered zero, and the same run with the name given delivered all of them.
- THE PAYLOAD IS THROWN AWAY. It is a doorbell and the answer still comes from the snapshot script, for two reasons: there is no artwork url in it (only "Has Artwork"), so a track change would have to ask anyway for the album colour; and track identity would otherwise have two definitions, one parsed from the script and one from a dictionary of Objective-C strings. Two copies of a fact is the shape of most bugs in this log.
- BETWEEN QUERIES THE POSITION IS ARITHMETIC. Checked against Spotify's own answer every five seconds for 92 seconds of one track: the largest disagreement was 1.4ms and there was no trend. Spotify's player position and this machine's monotonic clock are the same clock, so the reconciliation poll exists for seeks and not for drift.
- The window still hears a position every 300ms. That number did not move and must not: the predicted line swap is allowed to be ahead of the player by the choreography plus one of them. What changed is that most of those updates no longer cost an Apple event.
- RECONCILE_SECONDS = 1.0, and it is a trade stated as one. A query costs 4.3ms, so the loop costs 4.3ms/T: 1.43% of one core at 0.3s, 0.83% at 0.52s (one line change), 0.43% at 1.0s, 0.21% at 2.0s — against 19.6% for the subprocess. 1.0s buys most of what there is to buy and leaves a seek corrected inside about two line changes, which is the unit the window already moves in. The cost of the choice is honest: a seek made in Spotify's own window is picked up in up to 1.0s where it used to be 0.3s.
- A SEEK THIS APP MADE IS NEVER WAITED FOR. set_position, pause and resume all call disturb(), in a `finally`, because a command that failed is exactly as much of a reason to go and look as one that worked. The loop's wrap, tap-to-sync and echo practice move the position several times a song and none of them waits.
- Module-level rather than a monitor reference threaded through every QRunnable that sends a command, and that is the point: it makes it impossible to add a command that forgets.
- THE SLOWER RATE IS NOT EARNED, IT IS LOST. The first design earned it from the first announcement that arrived, which measured as no saving at all: announcements only arrive when something CHANGES, and a 60-second window on one uninterrupted song produced 197 queries — exactly the old rate. So it starts optimistic the moment the observer registers, and a track or state change discovered by asking with nothing having rung for it takes it away again. A Mac where the observer will not install, or a Spotify that does not announce, behaves exactly as this app did before any of this existed, and nothing has to sniff a version.
- The ring is counted AFTER the query and against the previous poll's reading, so an announcement that lands during a 133ms round trip still counts for the change that answer is about to report. Counted before, a track change racing its own announcement would read as a change nobody announced and the doorbell would be blamed for arriving on time.
- `_due` asks whether waiting for the NEXT tick would leave the answer too old, not whether it already is. Written the other way round it halved the rate in the one case that has to be identical to the old behaviour: two ticks nominally one interval apart differ by a float epsilon, and `elapsed >= interval` on them is a coin toss.
- THE LINE CHANGE, SECOND. 92.1ms of CPU reproduced today for what the log recorded as 92.7ms. The sampler said where: of the main thread's paint work, 61% was `sourcePixmap` re-rendering the source widget, and inside that `QPainter::drawText` alone was a third of every frame. Qt has no cache for sourcePixmap on a widget source, so two labels were being laid out and rasterised 37 times per line change for a fade and a 10px rise.
- Nothing about the source moves during a phase, so it is rasterised ONCE per phase: measured, 37.5 sourcePixmap calls per change became 2.2. The cache is invalidated at four funnels the window already had, and — layered on purpose — a repaint that arrives without `progress` having moved re-renders anyway, which is the state the window spends almost all of its time in and is the net under a fifth funnel somebody forgets.
- Qt does NOT call sourceChanged for a widget source's content, and that was checked rather than assumed: setText, setFont, setStyleSheet, a resize and hiding a row each produced exactly one extra draw and zero sourceChanged calls. So there is no Qt hook and the invalidation has to be the window's own.
- WITH THE TEXT NO LONGER RE-RENDERED, the window's own paintEvent became the largest single thing in a line change: two antialiased rounded rectangles over the whole window, clipped to a 460x45 band, 37 times. Between the corner radii the shape is not rounded — it is a rectangle with a vertical line down each side — so a damaged band inside that zone is drawn with three axis-aligned fills instead. That the pixels are the SAME is asserted rather than reasoned about: a test compares the two routes byte for byte over every band the window has, at 1x and at 2x, and at three glow widths.
- Together: 102ms per line change to 80ms by median over three alternating pairs on the same machine, best observed 60ms. The remainder is not ours to move — Qt's backing store, CoreAnimation committing the damaged band (with ~10% of the main thread in CGColorSpaceCreateWithICCData, which is macOS's), and PySide crossing into Python three times a frame. All of it is area times frames, and neither can change without changing how it looks.
- END TO END, the same 60-second window with music playing, alternating between the two revisions: queries to Spotify 197 → 66-78; the app's CPU including its subprocesses 21.8% of one core → 1.5%; Activity Monitor's energy impact 4.05 → 1.45; idle wakeups 105/s → 21/s. And on the rest of the machine, loginwindow 11.0% → 0.5%, tccd 8.6% → 0.05%, launchservicesd 7.7% → 1.1%, runningboardd 2.7% → 0.6%.
- The end-to-end figure is the cost of FOLLOWING a song, not of drawing one: LRCLIB was unreachable from the machine that day, so no lyrics arrived and no lines swapped in that window. The line change is priced separately, on a real window with a timeline of its own.
- The first version of the line-change harness measured 100% of a core in every condition, because it pumped the event loop with a processEvents() spin. A QEventLoop sleeps when there is nothing to do; what is left on the clock is then the window's own work. The second version replaced LineFade.draw with an instrumented copy and went on reporting the pre-cache numbers after the cache landed — it was measuring the implementation it had written. Both are worth writing down: a harness that agrees with itself is not a measurement.
- Two more doors, and two more guards: `player_monitor._cocoa` (NSAppleScript and NSRunningApplication, one door because the second exists only to decide whether the first may be used at all) and `player_events._distributed_center`. The subprocess guard used to cover Spotify and cannot any more, which is exactly the shape this project's guards exist for: the capability moved, so the door moved, and the alarm moved with it.

- Milestone 20 (the strip's own type size, a dock shaped like the notch, and the LRCLIB hit rate).
- THE BUG WAS A CONSEQUENCE OF MILESTONE 18'S OWN FINDING, and it took a user to name it. Milestone 18 proved that with the type scale following the window's width, the room for a line and the line grow at the same rate: (460 - 144) / T, the width cancels, and a line past 316pt at scale 1.0 fits at NO width. 18 used that to justify HOLDING the scale while the song chose the width. What it left in place was the other half: a strip whose type still followed its width whenever the song was not choosing it, so dragging an edge could not show one more character of a line. The report was "long lines elide and widening the window does not help", and the honest answer is that the window was behaving exactly as designed and the design was wrong.
- SO THE STRIP NAMES ITS TYPE SIZE, and the width goes back to being a width. Five presets in a submenu (14, 17, 20, 24, 28pt), following the speech rate's pattern, persisted in `window/compact_text_size`, with the default being `base_size(CURRENT)` itself rather than a second literal saying 20. Steps of about 20%, which is an ordinary type-scale interval. The full layout is untouched and that is the layers rule: there the type size IS the width, so a second control would be a second answer to one question.
- WHAT THE FIX LOOKS LIKE, photographed on the widest line in the 14-song corpus (Billie Jean, 82 characters) at 28pt type: 320pt wide shows "She's ju…", 560 shows "…who claim…", 900 shows "…(you kn…", and 1400 shows the whole line. Before this, all four showed the same words in different sizes.
- THE HEIGHT IS NO LONGER REMEMBERED, it is derived. A strip is one row of type and the type size answers how tall that row is, so `window/compact_height` was removed rather than left holding a number nothing reads. `_remember_size` keeps the full layout's height and the user's strip WIDTH, and nothing else. Vertical edges stop being resize edges in the strip for the same reason: an edge that showed a resize cursor and then refused would be worse than one that never claimed to, and what those edges do instead is move the window.
- THE ORDERING HAZARD THIS EXPOSED, and the test that caught it. `_apply_compact` used to compute the height floor from `self._scale`, which is the scale ALREADY APPLIED and lags a layout change by exactly the moment it is asked in. Moving `_apply_scale` before the resize fixed the strip and broke the way back: leaving compact, the scale was taken from the strip's width and the full layout came back with a 32pt gutter where it had left a 40pt one, which `test_compact_off_restores_the_layout_exactly` reported to the pixel. The fix is `_type_scale_at(width, compact)`, which answers about a shape the window has not taken yet: everything that changes the window's shape now takes the floor at the scale it is ABOUT to land on, and Qt cannot clamp a strip up to the floor it is trying to stop being.
- THE CAP CHANGED JOBS AND SO CHANGED VALUE, from half the screen to the screen. Half was the only thing standing between the user and a strip the width of their display while the type size was the width's to decide; with the size named directly, the control for "this is too wide" is the size. MEASURED over the same 776 lines from 14 songs: the widest window each song needs is 600 at 14pt, 717 at 17pt, 848 at 20pt, 1023 at 24pt and 1196 at 28pt. On the 1710pt screen these were measured on, the OLD cap never bound anything at 20pt and under (14 of 14 fit in half of it) and started binding only at the sizes that did not exist yet: 10 of 14 at 24pt, 6 of 14 at 28pt. Keeping it would have made elision a routine cost of choosing larger type, which is the bug again in a different place.
- A DOCKED WINDOW IS DRAWN AS A DIFFERENT SHAPE: square across the top, rounded underneath, flush against the underside of the menu bar. Two corners, and it is the whole effect — with them rounded the strip reads as a panel that happens to be up there, with a sliver of desktop showing through each corner; squared off it reads as the bar's own band continuing downwards, which on a notched Mac is the notch and on an unnotched one is the bar. Nothing about the POSITION changed; `docked_position` already put the top edge at `max(available.y, screen.y + top_inset)`, which is by definition the first row under the menu bar, so nothing reaches into it.
- RECOGNISED BY POSITION, NEVER BY A FLAG, and `geometry.is_docked` is now the one place that decides. It was already the rule inside `resized_position`, written out longhand; the paint needs the same answer, and two copies of it would be a window drawn as docked while being moved as floating. A flag would have to be cleared by every drag, every clamp, every nudge and every screen change, and the first one that forgot would leave a window claiming to be docked from the middle of a screen.
- ASKED IN FULL ON EVERY MOVE, because it is cheap enough to be: MEASURED at 8.9us for the whole question on this machine, of which 6.8us is the screen's safe area and 1.4us the two Qt rects. A drag delivering 60 moves a second spends 0.05% of one core on it, which is less than the alternative costs in ways to be wrong.
- AND IT RIDES WITH `_relayout` AND `showEvent`, not with `resizeEvent`. A hidden widget defers both its move and its resize events until it is shown, and plenty happens to a hidden window: the flight puts the position back BEFORE hiding it, a remembered position moves it, and the saved geometry is restored before anything is on screen. Without the showEvent call the first frame would be drawn in the shape the window had before all of that. This is the same trap `_relayout` exists for, found again one event later.
- ONE PATH BUILDS BOTH SHAPES, and the licence for that is a measurement rather than an argument: `_panel_path(rect, radius, square_top=False)` is byte for byte what `drawRoundedRect(rect, radius, radius)` produced, at 1x and at 2x, and a test pins it. Otherwise "square top corners when docked" would have quietly restyled every other window in the app. The straight-band fast path needed no change at all — between the corner radii the shape is a rectangle with a line down each side in BOTH shapes — and that is asserted for the docked one rather than assumed.
- THE MATERIAL IS A SEPARATE NATIVE VIEW AND HAD TO BE TOLD THE SAME THING. `CALayer.maskedCorners`, on the NSVisualEffectView's layer, which is unflipped so MinY is the pair under the window and MaxY the pair against the menu bar. A blur still rounded at the top under a scrim that is not would show the desktop through two small notches at exactly the corners the shape exists to remove. Verified by readback, like every other native state this window sets.
- LRCLIB IS BACK, AND THE HIT RATE FINALLY GOT MEASURED. 15 real tracks, taken from `.lyrics_cache/` so they are songs actually played on this machine, with Spotify's OWN metadata rather than a transcription of it: the harness drove Spotify to make each track current, read the album string and duration it reports, and gave the playing track, its position and its state back at the end (157.2s, still playing). Then the chain was asked sequentially, spaced 20s apart, twice, two minutes between rounds.
- THE ANSWER WAS NOT CLOSE. The first attempt — /get with the album — produced the answer 30 times out of 30, every one of them synced. Response times: 53ms fastest, 61ms median, 74ms at the 90th, 103ms at the 95th, 170ms slowest. Nothing below the album match was needed once.
- SO THE CHAIN IS HEDGED RATHER THAN FANNED OUT. An attempt is asked when the chain reaches it; the ones below it go out early only if it is taking long enough that overlapping them would save something. `_HEDGE_SECONDS = 0.25` is 4x the measured median and 1.5x the slowest response in the sample, so no lookup in it would have fanned out at all — two requests of every three simply not made. LRCLIB is free, runs on donations and is under load, and the brief's own instruction was to prefer the polite option when the numbers are close. They were not close; they were unanimous.
- THE COST IS STATED RATHER THAN BURIED, and it lands only in the case the concurrency was for. The same service was measured at 0.7 to 4.8 SECONDS per request in an earlier session; when it is that slow the hedge fires, the chain fans out exactly as it did before, and the lookup is at most 250ms longer than the all-at-once version. Against 4.8s that is 5%. Two other cases cost nothing at all: a 404 hands the floor to the next attempt at once, with no hedge to wait out, and an error on an attempt raises, so the ones below it were never going to be read.
- The sample's limits are worth writing down, because a measurement that oversells itself is worse than none. Fifteen tracks, one person's library, heavily K-pop, and every one of them a track that HAD lyrics — so the honest claim is "for tracks that resolve at all, the album match resolves them", not "the album match never misses". A track whose album name disagrees with LRCLIB's record still 404s and still falls through, at the cost of one round trip.
- A FLAKY TEST WAS FOUND AND NOT CAUSED. `test_a_band_is_drawn_straight_and_it_is_the_same_pixels` fails intermittently when its node is run on its own — 6 of 8 runs on an unmodified checkout of milestone 19, and it does not reproduce in-process over 40 trials with identical window state, `_docked` False throughout. It has never failed in a full-suite run. Recorded here rather than silently accommodated: the test's claim is sound and the test was not weakened, and the first thing the next session should know is that this predates milestone 20.

- Fix 20.1 (a red CI, and the flake that turned out to be the test).
- THE FAILING BOUND WAS A FONT MEASUREMENT IN DISGUISE. `test_the_strip_sizes_itself_when_a_song_arrives` asserted the fitted width landed under 460, which passed on macOS and failed on the Linux runner at 465. Nothing was wrong with the app: the fixture's longest line measures 246.00pt in the font macOS resolves for the offscreen platform and about 321pt in the one fontconfig picks, and 465 is exactly ceil(321) plus the two 72pt gutters. The line above it already asserted the width equals `expected_width(widest)`, so the fit was proven right and the bound was proving which machine the suite ran on.
- MEASURED, and the spread is the point: the same fixture line runs 237.14pt in Times New Roman, 246.00 in the platform default, 259.42 in Helvetica, 328.61 in Zapfino, 349.69 in Courier New and 350.62 in Menlo. A 48% spread, straddling the 316pt at which a strip stops fitting inside 460. Any test that names a pixel in a fitted width is naming a font.
- SO THE PROPERTIES ARE ASSERTED INSTEAD, and every one of them survives the font changing underneath: the width is what the pure arithmetic asks for given what was measured; neither the floor nor the cap is what decided it; the widest line fits with less than a pixel to spare, which is the "as small as it can be" claim itself; and nothing on screen is elided. The mirror case is asserted too — past the cap the window stops at the cap and the line ends in an ellipsis.
- AND THE GUARD IS A TEST RATHER THAN A RULE NOBODY RUNS. `test_the_fit_is_right_whatever_the_font_is` takes real families from the platform's own font database rather than naming any, re-fits under each, and asserts the tightness holds. It also asserts that the families it saw actually disagreed, because a portability test that only ever measured one width is the old test again.
- CHECKED BY RUNNING THE WHOLE SUITE UNDER A DIFFERENT FONT, twice: with the window's family stack forced to Courier New (349.69pt, which crosses the 460 the runner tripped over) and to Times New Roman (237.14pt), 1338 passed both times. That is the audit's real answer — no test in the suite depends on font metrics in a way a 48% change breaks.
- THREE MORE BOUNDS WERE FRAGILE FOR THE SAME REASON and were rewritten before they could fail: two `width() != 460` / `!= 500` assertions, which say "the song moved the width" but would fail on any platform whose font happened to fit exactly the width the test started from, and an outlier test asking the SCREEN's width where the window fits against the AVAILABLE width. The one surviving literal in that area (`width() == 460` in the strip test) is safe and now says why: no song is loaded, so there is nothing for the fit to measure.
- THE FLAKY TEST WAS THE TEST, NOT THE PAINTING, and the previous session was wrong to leave it as an unexplained intermittency. `img.copy(rect).constBits().tobytes()` hands back a memoryview onto a TEMPORARY QImage that PySide does not keep alive for it, so the copy can be released before `tobytes()` reads the buffer and the read returns whatever the allocator has since put there. - THE IDIOM NOW EXISTS ONCE, in `pixels_of(image, rect=None)`, and the other three sites were routed through it — two of which were already safe by accident because the image happened to be held in a local. An idiom that is safe by accident in three places and fatal in the fourth is exactly the shape the "one definition" rule is about.

- Milestone 21 (one menu, natively drawn, and grouped).
- THE BUG WAS THAT "ONE MENU" WAS ONE OBJECT AND TWO APPEARANCES. The menu bar item and the window's right-click menu had shared a single `QMenu` since the beginning, on the argument that two menus would drift apart. They never drifted, and they never looked alike either: Qt hands a system tray's menu to the Cocoa platform plugin, which converts it into a real NSMenu, so the menu bar route got the system's own font, check marks, separators and submenu timing, while `QMenu.exec` under the pointer drew Qt's widget style. Same object, same entries, same order, two menus.
- SO THE MENU BECAME A MODEL AND THE DRAWING BECAME A VIEW. `menu.py` was already the pure half (which entries are visible); it now holds the whole thing — an `Entry` tree with labels, kinds, submenus and preset lists, plus a `Menu` object carrying the live state and the one place a click lands. `nsmenu.py` is the only module in the app that says NSMenu, NSMenuItem or NSStatusItem. `window.py` kept the wiring and lost 130 lines of it.
- THE SPIKE CAME FIRST, AND IT WAS THE RIGHT ORDER. The whole idea rests on `popUpMenuPositioningItem:atLocation:inView:` working from an app that never activates, and this app never activates by design. Sixty lines of pyobjc, an accessory activation policy, a screenshot from a second process while the menu was up: it works, it does not bring the app forward, and the call blocks on its own modal tracking loop exactly as `QMenu.exec` did. Had it needed activation the milestone would have stopped there rather than after the refactor.
- THE MENU BAR ITEM HAD TO BECOME OURS, and that was the cost nobody would have chosen. Qt owns the NSStatusItem it makes and exposes no supported way to hand it a menu, so an app that wants ONE NSMenu on both routes must make the item itself. `QSystemTrayIcon` is gone, and with it the QIconEngine that milestone 15.1 measured into existence. Two things it was carrying were kept rather than re-derived: the item is now REMOVED in `_shutdown` (Qt used to destroy it with the widget, and an item this app makes outlives the window that answers its menu), and the glyph is still drawn at the screen's own scale.
- THE 15.1 CLIPPING LESSON SURVIVES THE QIcon GOING, and it is now stated more directly than the engine could state it. The bug was never about engines: it was that a 44-pixel image taken for a 44-POINT one is drawn into a 22-point slot with its top two thirds showing. `symbols.menubar_png(spec, points)` draws `points * ratio` pixels and `nsmenu` labels the NSImage `points` across. READ BACK OFF A REAL STATUS ITEM: `image.size()` is 22.0x22.0, its representation is 44x44 pixels, the button is 38x22 points and caches at 76x44. Photographed from the button's own drawing rather than from the desktop, because a full-screen app was hiding the menu bar: three bars, short / long / short, nothing clipped, tinted white by macOS because it is still a template image.
- WHERE THE ITEM IS CHANGED HANDS AND THE OLD MEASUREMENT IS WHAT LICENSED IT. The flight aims at `QSystemTrayIcon.geometry()`, and 15's note recorded that it agreed exactly with `NSStatusBarWindow.frame()` once Cocoa's origin was taken out. That agreement is now the implementation: `geometry.qt_rect_from_cocoa` does the one subtraction, `cocoa_point_from_qt` does the other direction for the right-click, and both are pure. Live, on this machine: the item reads (1129, 1073, 38x34) in Cocoa and (1129, 0, 38, 34) in Qt on a 1107-point screen.
- A GREY ROW IS STILL A GREY ROW, AND THE OBVIOUS FIX DOES NOT WORK. The remembered-apps list became disabled QActions when per-app forget was removed, and 14.2 replaced them with QWidgetActions because macOS greys a disabled item and four greyed rows read as four things that are unavailable. The native instinct is an attributed title carrying `NSColor.labelColor`. MEASURED, on a real menu, side by side with a plain disabled row: identical grey. AppKit dims a disabled item when it DRAWS it, whatever the string asked for. So the rows are NSMenuItems with a view (an NSImageView and a label), which is the QWidgetAction answer in the native idiom, and it was photographed: full-contrast names beside real app icons.
- THE READOUT ABOVE THEM STAYS A PLAIN DISABLED ITEM and that is not an inconsistency that was missed. One grey line among ticked entries reads as a note; four of them read as a broken feature. It also lost a hazard on the way: `QAction.MenuRole.NoRole` existed because Qt's text heuristic matches substrings and would have moved an entry reading "com.apple.systempreferences" into the application menu. A native NSMenuItem has no such heuristic, so the workaround went with the QMenu.
- CLICKS AND OPENINGS BOTH ARRIVE THROUGH ONE OBJECT. `nsmenu` defines exactly one Objective-C class, lazily and once, and it is both the click target and the menu delegate: neither holds state, and both are callbacks onto the same Python owner. Items carry an integer TAG that indexes a list of (key, value), so nothing Python-shaped crosses into Cocoa and nothing has to be kept alive on the other side. `menuWillOpen:` is the native `aboutToShow` and does the two things a refresh on a timer cannot do honestly: re-read what macOS says about the login item, and assemble the remembered-apps list.
- VERIFIED END TO END ON THE REAL PLATFORM, not just rendered: `performActionForItemAtIndex_` on the real NSMenu flipped the album tint from False to True and left the item's state at 1, the speech-rate submenu's fourth row handed 160 to the setter, and `menuWillOpen:` reached Python. The refresh sets every check mark and nothing else does, which is the `triggered`-not-`toggled` rule restated: `Menu.trigger` hands a toggle the state it is moving TO.
- SEVENTEEN ENTRIES IN ONE COLUMN WAS A LIST TO READ RATHER THAN A MENU TO USE, and the grouping is by what an entry is ABOUT. Top: show/hide, then what is on screen (Compact and its two settings, the album tint), then this song (romanisation, the spoken reference and its rate, echo practice, tap-to-sync), then two submenus, then quit. With every layer dormant that is four rows and two submenus against the eight entries it was.
- TWO RULES DECIDED WHAT COULD BE BURIED. Nothing that comes and goes with the song may go in a submenu: an entry that has just appeared because it can now act is one somebody is looking for, and a submenu is one more click and one more place to look. And a setting's detail sits directly under its own switch, which is why Compact text size and the fit follow Compact rather than joining a "display" group, and why Speech rate follows Spoken reference.
- THE TWO SUBMENUS ARE POSITION AND SYSTEM. Position is Dock to top, then per-app memory entire (the toggle, the readout, the list, forget-all): one question, where does this window sit. System is Spaces, the notification yield, the menu bar animation and Open at Login: how the app behaves in somebody's machine rather than in their song. Dock to top moved away from Compact, and the pairing that put them together is not contradicted: that argument was about VISIBILITY (both answerable with nothing playing) and both are still always visible.

- Milestone 22 (getting out of the pointer's way).
- THE FEATURE EXISTS BECAUSE THE ONE IT REPLACES IS NEVER USED. Option and a scroll over the window has adjusted opacity since milestone 4 and it works. It also has to be remembered, aimed and undone, which is three deliberate acts for a problem that lasts two seconds, and the brief for this session was one sentence of lived experience: the opacity gesture is rarely reached for and moving the window would be preferred. So the pointer arriving over the window IS the request now, and the setting is what the window does about it.
- THREE VALUES, DEFAULT OFF, in the System submenu directly under Yield to notifications, because it is the same sentence said about a different intruder: that one gets out of the way of a banner, this one gets out of the way of the hand. `proximity.py` is pure and Qt-free like every other rules module; `window.py` supplies two rectangles and a pointer and does what it is told.
- DODGE MOVES AND GHOST DOES NOT, and neither is a better version of the other. Dodge vacates its rectangle so what was under the window is visible AND clickable; Ghost stays put, fades to a ceiling and sets `ignoresMouseEvents` so the clicks land on whatever is behind it. The first is for a window parked over something you look at, the second for one parked over something you click. Ghost borrows nothing that has to be given back except a number, which is the argument milestone 16 made for fading rather than moving; Dodge is the case that argument does not cover, and it pays for the move with a held home position.
- THE POLL IS THE SAME POLL, and it had to be. macOS delivers enter, leave and mouse-moved events only to the ACTIVE application; this one is an accessory that never activates, which milestone 18 measured with the real pointer on the real window and found `hovered` stubbornly False. Ghost makes that mechanism load-bearing twice over: a window that ignores mouse events would not hear an enter event even if one were coming, so the thing that notices the pointer LEAVING is the one thing the click pass-through cannot switch off. The compact layout's controls and this layer read one reading of `QCursor.pos()` per tick rather than each taking their own, because the pointer is entitled to move between two calls and the two layers would then be acting on different answers to one question.
- THE POLLING COST, MEASURED, 200,000 iterations each on this machine: `QCursor.pos()` is 0.309us, the frame test takes the poll to 0.714us, and the region test this layer adds takes it to 0.973us. At 100ms that is 0.00097% of one core, and the ADDED 0.258us is 0.00026% of one. Working out where a dodge goes costs 0.852us and happens once per arrival rather than once per poll. The timer still runs only while the window is showing and one of the two layers wants it, which is the cheapest half of "poll only as often as needed": the difference between polling and not polling at all.
- THE TRIGGER REGION IS ANCHORED ON WHERE THE WINDOW BELONGS, and that one decision is what makes Dodge possible at all. A region that followed the window would report "clear" one poll after reporting "covered", every time, for ever: the window flees the pointer, the pointer is therefore no longer on it, the window comes home, the pointer is on it again. Home is a rectangle the dodge cannot change, so the oscillation has nowhere to start.
- LEAVING TAKES BOTH RECTANGLES, and the second half is what makes a dodged window catchable. The pointer must be clear of home AND of where the window actually is, each by the release margin. Without it, following the window would leave the home region, the window would come home, and it would arrive where the pointer no longer is: a window you can see and can never click. With it, following it is not leaving it, and a press on the window it caught adopts wherever it stands as the new home.
- THE HYSTERESIS BAND IS 12 POINTS AND IT IS SET BY EYE, which is said here rather than dressed up. What was measured is what it is NOT for: sampled at the poll's own 100ms for 30 seconds with nothing touching the trackpad, the pointer reported the identical coordinate 300 times out of 300. There is no jitter to absorb and a band of zero would not flap on a resting hand. It exists for the deliberate small movement, a pointer parked on the window's edge while its owner reads something, and for that there is no threshold to find. The cost is one poll: a pointer crossing 12 points at 120 points a second spends 100ms inside the band, which is the interval the window is asking at anyway.
- ONE NUMBER, TWO USES, and it is the same question asked in the other direction. The dodge leaves the release margin of daylight between where the window was and where it went, because a window that stepped aside by exactly its own height would put its new edge on the pointer's old position, which is inside the region it just left.
- THE DODGE VACATES THE WHOLE FOOTPRINT rather than sliding far enough to uncover the pointer. Sliding the smaller amount answers the literal question and nothing else: what somebody reaches into a window for is the thing the window is on top of, which is a region and not a point, and a strip that dropped fifteen points would still be over most of it. Ten points of travel with the thing you wanted still hidden is worse than not moving, because it looks like the feature worked.
- AND THE AXIS FALLS OUT OF THE WINDOW'S OWN SHAPE WITHOUT BEING NAMED. Four candidates, each clearing the footprint, ordered by travel: a strip 900 across and 40 tall steps vertically because that is 52 points against 912, the full layout at 460x200 steps vertically for the same arithmetic, and a tall narrow window would step sideways. Nothing decides an axis; the shape does. Ties inside an axis resolve by a fixed order, because a window that stepped up one song and down the next would read as random. Every candidate is clamped like any other placement of this window, and one that needed no clamping is preferred over one the screen dragged back, so a window near an edge does not step half off it when the other direction was free.
- NOWHERE TO GO IS AN ANSWER AND IT IS SAID. A window shuffled to a position still under the pointer would dodge on every arrival and uncover nothing, so `dodge_destination` returns None and the window stays put. It takes an absurd screen to reach — clamping leaves a strip of the grab margin clear at each edge, so the answer is only None when the available area is under two margins across in both axes, about 80 points — and the branch is exercised rather than left as one nobody can picture.
- A TEMPORARY POSITION IS NEVER WRITTEN DOWN AS A PERMANENT ONE, which is the flight's rule arriving for the third time. `_proximity_home` holds the real position for as long as the window stands aside, exactly as `_flight_home` does for as long as it is away, and `_home_pos()` is what the save at shutdown and the per-app learn ask instead of `pos()`. The three things that move the real position while it is borrowed — a remembered-position move, docking, the song changing the strip's width — write the HOME and derive the standing-aside position again from it, which is the same sentence `_dock_to_top` already contained for the flight.
- FITTING AND THE POINTER DO NOT BOTH OWN THE WIDTH. `_resize_width_to` measures from the home rectangle, because everything the anchoring rule cares about is a property of it: whether it is docked, and where its centre is. Anchored on a dodged one, a song would centre the new width on a temporary position and then hand that back as the permanent one.
- EDGE TRIGGERED, NOT LEVEL TRIGGERED, and that one rule is what makes every suspension tolerable. The behaviour begins on the pointer ARRIVING and ends on it leaving; nothing restarts it in between. A sync pass starting over a dodged window brings the window home and leaves it there, and when the pass ends with the pointer still on the window nothing steps aside under a hand that is still using it. The pointer has to leave and come back, which is a thing the user does rather than a thing that happens to them. `Approach` keeps two booleans and not one for exactly this: whether the pointer is on the window is a fact about the pointer, and whether the window may act on it is the gate.
- SEVEN SUSPENSIONS, AND THREE OF THEM ARE ONE SENTENCE: the user needs to click this window. A tap-to-sync pass is a rhythm game played on a button on this window once per line, and ghosting it would send the taps through to whatever is behind. An echo attempt pauses the song and hands the turn over with the done button as the only way out, which is also the one state where the compact layout already holds its controls out whatever the pointer is doing. The failure register is open because somebody clicked the ⓘ, and the click that closes it is the same click on the same control. The other four are "something else owns this window": a hand on it, a flight to or from the menu bar which owns both position and opacity until it lands, a hidden window which is in nobody's way, and the layer being off.

The window's own right-click menu is unreachable in Ghost: a right-click passes through to the app underneath, and the menu bar item is the way in. That is inherent to click-through rather than an oversight, and the menu bar item is the same answer the app already gives for a hidden window. A native NSMenu on screen is not suspended either — AppKit runs it on a nested modal loop with no close notification to observe, and the window is under the menu rather than under the pointer.

- Fix 22.2 (the loop's wrap seek, sent twice).
- THE REPORT WAS AN AUDIBLE ARTEFACT AT EVERY WRAP AND A LOOP THAT CANCELLED ITSELF after one or two of them, in both layouts, on a song with nothing exotic about it. The hypothesis on the table was staleness: Spotify announces nothing on a seek (milestone 19 measured that), so the monitor would carry the position forward past the loop's end bound and `still_valid` would read the app's own wrap as the user seeking away. THE HYPOTHESIS IS REFUTED, and the trace that refutes it is worth more than the fix would have been.
- THE POSITION IS NOT STALE, AND TWO THINGS ALREADY GUARANTEE IT. `disturb()` is called in a `finally` by every player command, and `run()` waits on that event rather than on the clock, so the seek's own landing ends the wait and the query goes out inside a round trip. And every question and every command share one `_ask_lock`, so a query cannot execute while a seek is executing: an answer that comes back after a seek is an answer that was READ after it. Measured over a 10 second line looped for 45 seconds, at round trips from 0.133s to 1.0s: the worst disagreement between the position the window was told and where Spotify actually was is 0.000s.
- THE BUG IS THE LOOP'S OWN SCHEDULING, AND IT IS OLDER THAN MILESTONE 19. The wrap is dispatched a seek lead (0.46s) BEFORE the end bound, and the round trip that carries it takes most of a poll interval. Every position that arrives in between is still inside the lead, so `wrap_eta` clamps to zero, the window arms the timer for 0ms, and `_do_loop_wrap` — which had no memory of having already dispatched one — sends the seek again. Measured: 7 to 8 seeks where 4 were wanted. What that sounds like is the line restarting, playing for a round trip, and restarting again. Simulated under the PRE-19 regime as well (a real query every tick, the seek in its own subprocess): 7 to 8 seeks there too. Nothing about the doorbell caused it.
- WHAT MILESTONE 19 DID CHANGE IS WHAT THE EXTRA SEEKS COST. They queue on the one lock, ahead of the reconciliation query that would have told the loop it had already wrapped — so the wrap the user is waiting for lands later, and the player really does run on past the end bound. `still_valid` is then reading a TRUE position and cancelling correctly. Measured across ten phase offsets: at a 0.5s round trip, 8 to 9 seeks and no cancellation; at 0.7s, cancelled in 10 runs out of 10 after two or three wraps, with the player 1.77s past the end bound. That is the reported symptom exactly, and it is why the two halves of the report have one cause.
- ONE WRAP IS OUTSTANDING AT A TIME, AND A POSITION EARLIER THAN THE ONE IT WAS DISPATCHED FROM IS WHAT SAYS IT LANDED. A seek is the only thing that moves a position backwards, so nothing else can be mistaken for one. The dispatch point is `end - SEEK_LEAD_SECONDS` and the controller derives it rather than being told: the scheduler runs the timer for exactly `end - position - lead`, so that is where it fires whatever position armed it. A wrap that never lands replaces nothing, the position runs on, and `still_valid` cancels — which is what a failed seek has always done and is the one behaviour that must not be papered over. After the gate: 4 seeks at every round trip up to 1.0s, and cancellation only at 1.5s, which is past `EXIT_GRACE + SEEK_LEAD` and is a seek that really has failed.
- THE ANTICIPATORY LINE CHANGE ALREADY HAD THIS RULE AND THE LOOP DID NOT. `LineTransition.may_arm`/`begin` exists because a poll landing mid-choreography re-armed the fade timers and played the same line change twice — the same shape, the same cause, found two milestones earlier and solved in a pure module. The loop's scheduler was re-armed from every poll with nothing claiming the movement.
- WHAT THE AUDIT FOUND EVERYWHERE ELSE, INCLUDING WHERE IT FOUND NOTHING. Echo practice is not exposed: its wrap dispatches a PAUSE rather than a seek, and the ATTEMPT phase suppresses `wrap_eta` from the first wrap onward, so there is no second dispatch to make; the done button's seek-then-resume runs while the player is paused, and `wrap_eta` returns None for a paused player, so nothing can arm behind it either. Driven through the real monitor at round trips from 0.133s to 1.0s: one pause per attempt, one seek per replay, no cancellation. The anticipatory transition has `may_arm`. The tap stamper interpolates from `_last_position`/`_last_polled_at` and is exposed only in the round trip after `_begin_sync` seeks to zero, which is seconds before the first line it could stamp, and `MAX_EXTRAPOLATION_SECONDS` bounds it at 2.0s. The sync pass's seek to zero is the same window and has nothing reading a position inside it.
- A SEEK THIS APP MADE IS AN ANSWER AS WELL AS A QUESTION, and that is a second fix with a measurement of its own rather than a rider on the first. `poll_once` clears the wake BEFORE the query and returns None when the query raises, so a transient failure SPENDS the disturb and the next answer is a reconciliation interval away. Measured with one failed poll after a wrap seek: the window was told a position 9.673s from where Spotify was. `moved()` records where this app put the player, `_rebased` applies it to the carried-forward answer, and the same measurement is 0.000s. Recorded on success only, while `disturb()` stays in the `finally`: a seek that failed moved nothing, and claiming otherwise would paper over the one signal a failed seek has.
- AND IT IS ASKED OF THE LAST ANSWER, NEVER OF A FRESH ONE. The first draft rebased inside `poll_once` too, for the race of a query already in flight when the seek lands. That race cannot happen: the lock means the seek waits for the query, so a fresh answer is always stamped after any seek that has finished, and the branch could not have fired. Removed rather than kept as insurance, because a branch no test can fail is a comment. The stamps are comparable for the same reason — both are read the instant that call's own round trip came back, and the round trips do not overlap.
- ADDING THE RECORDING BROKE A TEST BEFORE ANY OF THIS WAS WRITTEN DOWN, which is the module-state fixture earning its docstring. `_moved` is stamped with the real monotonic clock, and the suite's monitor tests run on a fake one starting at 1000.0, so a seek left behind by one test is a move from the far future for every test after it: a carried-forward position of 10.3 came out as -599689.0. It is cleared around each test now, beside `_wake` and `observing`.
- 1487 TESTS PASSED AGAINST A LOOP THAT SEEKED TWICE AT EVERY WRAP, and the reason is one sentence: every loop test handed `LineLoop` a position and asked what it decided, and every window test handed `_on_position_update` a snapshot it had built by hand. Both are the caller answering its own question, and the bug is a disagreement between the scheduler and the PLAYER. So there is a player in the suite now — a fake Spotify and a fake clock under the real `PlayerMonitor`, wired to the real window's real slots, with the real loop and the window's own timer arming — and the only things that move the position in it are playback and this app's own seeks, which is the situation a loop actually lives in.
- THE HARNESS HAD TO BE WRITTEN TWICE, AND THE FIRST VERSION PASSED AGAINST THE UNFIXED LOOP. Stepping the clock a poll interval at a time puts every command landing before the tick that follows it, so the window between a seek being SENT and it LANDING never contains a poll — the entire gap the bug lives in, stepped over. It advances to whichever of the three events is next instead: the tick, the wrap timer, the landing. The wrap timer is on the fake clock for the same reason, because a real QTimer can only fire when the window asks for 0ms and the wrap would then always be dispatched at the instant of a tick.
- FOUR MUTANTS, ALL RED IN THE RIGHT PLACES. The loop's gate removed: 4 unit tests and both integration tests. The window not telling the loop where the player is: both integration tests. The monitor's rebase removed: the two monitor tests, and NOT the integration tests — which is the honest result, and says out loud that the rebase is not what fixes the reported bug. A failed seek recorded as a move: the two tests that exist to forbid it.


- Fix 22.3 (a lead that is measured, a press that is traced, and two layouts that are two shapes).
- THE SEEK LEAD WAS A CONSTANT AGAINST A VARIABLE AND THE REPORT WAS THE ARITHMETIC. 0.46s was inherited from the osascript era, when the write was measured at 150-200ms; in-process the same command was measured between 133ms and a full second in one session, because it queues on the one `_ask_lock` behind whatever the monitor happens to be asking. The wrap is dispatched a lead before the line's end so the seek LANDS on it, so the error IS `round_trip - lead`. Simulated on a 10 second line at five round trips: the fixed lead cut 0.36s off the end of every line at 0.10s, 0.33s at 0.133s, 0.21s at 0.25s, and let 0.24s of the next line through at 0.70s. Early nearly always, late occasionally, which is the report word for word.
- SO THE APP MEASURES ITS OWN. `player_monitor._send` times every command at the one point they all go through, which is what makes it impossible to add a command that is not timed, and the timing is around the WHOLE of `_ask` — the wait for the lock is how long the command took to reach Spotify and the lead has to cover all of it, and that queueing is the entire reason the number varies. Recorded on SUCCESS only, for the sharper half of the reason `moved()` is: a failure that timed out waited two seconds for nothing, and writing that down would put the lead on its ceiling on the strength of a command that never happened.
- THE STATISTIC IS THE MEDIAN AND THAT IS THE WHOLE OF THE OUTLIER HANDLING. No threshold to argue about and no constant to justify: one command that queued behind a slow query moves the middle of eight samples by nothing at all, and it takes five of them agreeing before the lead follows, which is about three wraps of a ten second line. A machine that has genuinely got slower is tracked within a verse; a hiccup is ignored entirely. The floor is 0.05s and the ceiling is `EXIT_GRACE`, which is not a coincidence but the argument: a round trip past that is one `still_valid` is about to cancel the loop over, so a lead chasing it would be eating the line to protect against something that is not survivable.
- THE RESULT, MEASURED THE SAME WAY THE PROBLEM WAS: within 1ms of the line boundary at every round trip from 0.10s to 0.70s, from the SECOND wrap on. The first wrap of a session has nothing to go on and is out by whatever the round trip differs from `SEEK_LEAD_START` (0.20s, which is the measured 133ms plus most of another, so it errs early rather than late) — measured at -0.10s to +0.50s. One sample IS the median, so it converges in one wrap rather than over a verse.
- AND IT BROKE THE LANDING TEST, WHICH IS WORTH MORE THAN THE FIX. `_wrap_from` was `end - lead`, reconstructed at dispatch. The moment the lead stopped being a constant the reconstruction stopped agreeing with what happened: a lead measured SHORTER between arming the timer and it going off puts `end - lead` later than the position the wrap really went out at, so the very next poll read ordinary playback as the seek landing and dispatched a second one. Measured, at a 0.10s round trip: two extra seeks in five wraps, found in the trace and not in the suite. The threshold is now the last position actually SEEN, because playback only moves forward and nothing playing on can fall below where the line already was. Same shape as the rule about refusals: a reconstruction can disagree with what happened.
- THE MISSED PRESSES WERE INSTRUMENTED AND THEN REPRODUCED, and the instrumentation is what stays. Every press is traced at DEBUG through ONE method whichever object received it (an event filter on each control plus the window's own handler), because two records of one event written in two places is how they come to disagree. It carries the global position, what `childAt` resolved to, every control's rectangle in the same coordinate space whether it is on the window or not, the frame, the device pixel ratio, the layer's affine transform read BACK rather than reconstructed from `_flight_progress`, and which of the five animations were running.
- IT REPRODUCED ON THE THIRD ATTEMPT AND THE FIRST TWO ARE THE LESSON. The first probe's own successful press on the mic button ended the echo attempt, so every case after it was measuring a state where the button was correctly absent — four confident MISSED lines, all of them the harness. The second stepped the clock in poll intervals, which put every command landing after the tick that follows it. What settles it: with the app backgrounded and real CGEvents posted at each control's live centre, in the compact strip, a press 0ms, 15ms or 30ms after the pointer arrived reached the WINDOW; one 45ms or later reached the control.
- THE CAUSE IS NOT HIT TESTING AT ALL, AND THREE SUSPECTS WERE CLEARED BY MEASUREMENT. The layer transform is the identity after a flight there and back (a=1.0 d=1.0 tx=0 ty=0, read off the layer). Presses during an animated resize, during a move animation and during a flight all reached the control. What is actually happening is that there is no control there yet: macOS delivers no hover events to an app that never activates, so the strip's controls come out when the POLL notices the pointer, up to 100ms later, and a hand with muscle memory beats it. A posted CGEvent at the control's live geometry acts correctly at every commit for exactly that reason — the probe moves and clicks with the control already out.
- THE PRESS IS ITSELF A POINTER READING, and a better one than the poll: exact, and now. A press ON this window IS a pointer on this window, so there is no region test and no second reading — the event brought the answer with it. It cannot rescue THAT press and does not pretend to, because Qt chose the receiver before any of this ran and a control that is not on the window is not one a press may be re-aimed at; what it does is start the reveal when the hand arrived rather than when the next poll happens to run.
- THE SECOND DEFECT IS THE ONE THE USER ACTUALLY SEES, AND IT IS A ONE-LINE RULE. Every press that misses a control lands on the window, every one of those ends a "drag" of zero pixels, and `mouseReleaseEvent` recorded a position and lit the learn glow for every one of them — so the app answered a press meant for a control by announcing that it had learned something. `learn_refusal` gained `moved`, and the reason names itself. Learning is implicit, which is exactly why it may only follow an act that meant it, and `_learn_position`'s own docstring already said "a drag or resize ENDS" while the code said any press and release at all.
- POSITION AND SIZE ARE ONE FACT AND WERE HALF REMEMBERED. The size half has worked since milestone 20 and was verified in every path before anything was changed — the menu toggle, a sync pass borrowing the full layout, a fitted strip, and across a restart, all four give the full layout its size back. What was missing is where. Probed: full at 300,200 sized 520x340, into the strip, moved to 120,60, back to full — 520x340 at 120,60, and the strip's own place lost too. Worse with lyrics loaded, where fitting the strip's width anchors on the centre: 0 to 130 to 260 across two switches, a hundred pixels a time.
- SO ONE RECORD PER LAYOUT (`placement.LayoutShapes`), AND WHAT IS NOT IN IT IS AS MUCH OF THE DESIGN AS WHAT IS. The strip has no remembered height, because it follows the type size and there is one right answer. Its width is not written while the song is choosing it — but its POSITION is, because the song has an opinion about how wide the strip is and none at all about where it sits, and losing the place because a song happened to be fitting would answer a question nobody asked. The position kept is `_home_pos()` and never `pos()`, which is the temporary-position rule for the fifth time.
- GIVEN BACK AFTER THE FIT, NOT BEFORE, and clamped. Fitting anchors a width change on the window's centre, so restoring the place first would have the song move it again; clamped because a remembered position is a preference expressed on a display that may be gone. A layout never worn is left where the resize put it rather than moved to a place nobody ever chose — the same answer `_width_for` already gives about a width nobody has picked — and the centre-anchoring rule is then still the only thing deciding where it goes.
- SIX MUTANTS, ALL RED IN THE RIGHT PLACES: the learn without the moved check (2 tests), the press not saying where the pointer is (1), the lead back to a constant (5), the landing threshold back to `end - lead` (2, including the loop's own end-to-end test at a slow round trip), a failed command timed anyway (1), and the layout position never given back (3). Resilience: the backoff, the manual retry, pasted lyrics, and warming the album (suite 1622 → 1694)
- FOUR THINGS ABOUT AN OUTAGE, and they are one session because they are one situation: LRCLIB is down or slow, and the app should cost it less, tell the user more, still be usable, and have less to lose. Plus one correction, which is the other half of an entry above.
- THE RETRY SCHEDULE GROWS AND THE GROWTH IS MEASURED. "lyrics unavailable, will retry" meant every 30 seconds for as long as it lasted, so a song left on screen through a three hour outage made 360 requests of a free service that was already having a bad day, all asking the same question. It now doubles from 30 to a ceiling of 300: 30, 60, 120, 240, 300. Over three hours that is 38 requests against 360, and the saving holds at other lengths — 14 against 120 over an hour, 98 against 960 over eight, so 8.6x, 9.5x and 9.8x, rising, because past the ceiling both schedules are linear and the growing part is a smaller share of a longer outage. The FIRST retry is deliberately unchanged: most failures are a blip and the promise on screen is answered at the speed it always was.
- THE CEILING IS 300s BECAUSE OF HOW LONG SONGS ARE, which is a measurement of the right thing rather than a round number. A track change re-attempts immediately whatever the schedule says, so the ceiling only ever governs a song LEFT UP. Of 69 tracks across 5 real albums (ground truth from the iTunes catalogue) the median is 232s and 88% run under 300s, so for seven songs in eight the next track beats the ceiling to it. Longer would be a number that almost never applies; shorter would be spending requests to be ready for a moment that has already passed.
- ONLY AN ANSWER FROM LRCLIB RESETS THE COUNT, and that distinction is the whole design rather than a refinement. "The lookup succeeded" and "the service is answering" are different facts: during an outage every song the user has played before still answers instantly from the cache, so a counter that reset on those would be back to a 30 second retry on every uncached track — a backoff that stops backing off exactly when somebody is listening to music. `LyricsProvider.look_up` therefore returns a `Lookup` naming the SOURCE (user sync, cache, warmed, lrclib), `get_lyrics` stays what it was for every older caller, and one boolean crosses the fetch signal.
- THE COUNT SURVIVES A TRACK CHANGE AND A STOP, for the same reason: an outage is not a property of the song on screen. `_reset` clears the display and leaves it.
- RETRY-AFTER IS THEIRS AND OUTRANKS OURS. LRCLIB's API documentation asks callers to honour the header on a 429 and says ignoring it may result in a temporary ban. So a 429 starts a HOLD, and the hold is checked inside `_fetch_json` rather than in front of the retry timer — because the retry timer is one of three ways a request leaves this app, and a hold that only quietened the retries is one a user skipping tracks walks straight through. It is module level for the connection pool's reason: it is a fact about the HOST, and a hold that covered only one provider object would be no hold the moment there were two.
- A LOOKUP THIS APP REFUSED IS NOT A FAILURE OF THEIRS. The refusal surfaces as a failure the window can show and explain — kind `HELD`, "waiting, as LRCLIB asked" — and `failure.reached_lrclib` is what keeps it out of the count: counting it would grow the backoff on the strength of the backoff, and the interval would run away from the user while LRCLIB sat there healthy. It is a function rather than a field, so the boolean is derived from the reason and the two cannot disagree.
- AND IT IS NOT STAMPED WITH AN ATTEMPT. `LyricsError.at` leaves a `HELD` failure alone, because it belongs to no link of the chain: it happens before a request is made and would have happened at every attempt equally. "Waiting, as LRCLIB asked · album match" reads as though the album match were what was waiting, and that is what the first version said.
- ONLY 429 GETS A SENTENCE OF ITS OWN. Every other status is still "LRCLIB answered HTTP nnn"; this one says "LRCLIB asked this app to slow down", because it is the one status the app DOES something about rather than only reports, and a person reading "429" learns less than the app already knows.
- THE HEADER IS READ AS SECONDS AND NOTHING ELSE. RFC 7231 also allows an HTTP date, and reading one would mean trusting this machine's clock to agree with theirs — a skew turns "wait 30 seconds" into a pause of hours or none at all. A header this app cannot read is treated as no number rather than as a guess, and the caller still backs off on its own schedule. Matched without regard to case, because field names are case-insensitive and a lookup that only knew `Retry-After` would read `retry-after` as "they did not ask us to wait".
- THE RESPONSE CARRIES ITS HEADERS NOW, as the pairs `getheaders()` gives rather than a dict, because a response may legitimately repeat a field. Exactly one of them is ever read. Read BEFORE the connection is given back or closed, like the body above it: what is handed to the caller has to be values, not a handle onto a socket `_exchange` is about to let go of.
- THE MANUAL RETRY SITS BESIDE THE REASON, NOT BESIDE THE MESSAGE, and that placement is the argument. The message already says "will retry" and means it, so a button next to that sentence would be inviting people to do the thing the app has just promised to do for them. Beside the REASON it is for somebody who opened the explanation, read it, and knows something the schedule does not — the wifi is back, the VPN is off. It appears with the reveal and goes away with it.
- IT RESETS THE SCHEDULE AND CANNOT WAIVE THE PAUSE. Pressing it takes the interval back to 30 seconds, because a person who has looked has better information than a counter; if they are wrong the next failure starts where it would have started anyway. What it cannot take back is Retry-After: that is a condition of being allowed to ask at all, so the press goes out, is refused at the provider's door before a socket is opened, and the reason says so. Driven end to end in the integration tier, with the press delivered to the top-level `QWindow` so Qt picks the receiver — which also closes the audit row that said the `why` button was the one control never pressed through Qt.
- TAP-TO-SYNC NEEDED LRCLIB TO WORK, WHICH IS BACKWARDS. It could only start from plain lyrics the service had answered with, so during an outage the one feature that works entirely offline could not be started at all. It can now start from lyrics the user pastes in, saved into `.user_syncs/` exactly as before, reloaded from there afterwards, and reachable with no network at any point.
- THE PASTE ENTRY POINT IS A SECOND WINDOW, and every reason is a rule the lyrics window is built on. That one is frameless, `WindowDoesNotAcceptFocus`, `WA_ShowWithoutActivating` and mouse-only, because it is an overlay that must never take the keyboard from whatever the user is doing — and a text field is the single thing none of that can support. So the box is an ordinary system-drawn top-level with a title bar, gone the moment the pass begins. It borrows exactly one thing from the overlay: staying on top, because otherwise it is the one window a user could lose behind the one they opened it for.
- AND IT COULD NOT TAKE THE KEYBOARD, WHICH ONLY THE REAL PLATFORM COULD SAY. Under the accessory activation policy, `show()` + `raise_()` + `activateWindow()` leaves the window inactive and the focus widget None — measured, by running it: False and None. An accessory app has no Dock icon to be activated through, so it has to activate itself, and with `activateIgnoringOtherApps_(True)` first the same three calls give True and the text box. No headless test could have caught this; the offscreen platform reports whatever it likes about focus. NSApplication now has one door (`_nsapp`), shared with the activation policy that was already using it, and a structural test keeps it to one.
- PASTED LRC LOSES ITS SYNTAX. What people have to hand is frequently a `.lrc` from somewhere: left alone, every line of the pass would read "[00:12.34] words" and the sync saved afterwards would carry a second timestamp in front of the first. Stamps at the start of a line are stripped and the words kept, metadata tags go entirely (a pass that made somebody tap through four of `[ar:...]` before the first lyric is one they abandon), and a bracket in the MIDDLE of a line is left alone, because that is somebody's punctuation and guessing further about a person's own words is how a sync loses the line they were waiting for.
- THE TWO WAYS INTO A PASS ARE MUTUALLY EXCLUSIVE BY CONSTRUCTION. "Paste lyrics to sync" is offered exactly where "Sync this song" cannot be — a music track with no lines to stamp, which is ERROR and NO_LYRICS — and the gate is asked of the view model rather than trusted to the menu, so pasting can never become a second way to overwrite lyrics that are already there. The menu group gains a row rather than a column.
- WARMING THE ALBUM TOOK TWO ROUNDS. Spotify's scripting dictionary describes the CURRENT track and nothing else — there is no way to ask it what else is on the album — so the track list has to come from LRCLIB too. Round one is one `/api/search` for the album; round two asks `/api/get` per name it returned.
- MEASURED AGAINST 4 REAL ALBUMS (47 tracks, ground truth from iTunes). Serving the search's OWN records under a duration check tight enough to trust covers 19% of an album, because the durations in a search hit are frequently a different recording's. Asking `/get` per name instead reaches 47%, and 17 of 20 answers agreed with the real duration within 2s. Both rounds run on every album, which costs one search and about 19 gets, of which the measurement found 29% useful; the rest of the names are karaoke versions, medleys and mislabelled uploads, and nothing about them says so up front. SUPERSEDED below: the second round is not worth paying for an album nobody listened through.
- FILTERING THE NAMES BY ALBUM WAS MEASURED AND IS WHY THERE IS NO FILTER. Keeping only records whose `albumName` matches the one playing costs 24 requests and reaches ZERO of the 47 tracks: LRCLIB's album names are user-supplied and rarely spelled the way Spotify spells them. The obvious tidying would have turned the feature off.
- A WARM ANSWER IS CHECKED AGAINST THE `/get` TOLERANCE, NOT THE SEARCH ONE. It stands in for the album match rather than for the search, so 2s rather than 10s: anything looser would quietly demote every track it touched from an exact answer to a search-shaped one, which is the priority-order rule the chain has always had. The check earns its keep at the measured rate — 3 of 20 warmed tracks were a different recording, and those three fall through to the ordinary chain.
- THE WARM STORE CAN SAY YES AND IT CAN SAY NOTHING. It can never say "this track has no lyrics": it is a guess made without the track in hand, and a guess may not stop the real question being asked. A hit is promoted to an ordinary cache entry on the way past, so the second play takes the fast path and the duration is never checked twice. It lives INSIDE `.lyrics_cache/`, deliberately and for the mirror of the reason `.user_syncs/` does not: this is the one thing here nobody made, so clearing the cache must take it.
- SEQUENTIALLY, WITH A GAP, BECAUSE THEY ASKED. LRCLIB's documentation names batch work like library scanning and asks for one request at a time with 200 to 500ms between them; the gap is 350ms, the middle of that band, and it is what the coverage measurement above was taken at with no 429. The requests go out on a worker five seconds after the song's own lookup landed, which is set by eye and says so — everything it has to clear (the two second title card, the artwork fetch nobody waits on) is over by then.
- AND IT DOES NOT RUN WHILE THE SERVICE IS FAILING. Skipped in ERROR, skipped while the failure count is anything but zero, one album at a time, once per album ever, and a single failure ends the album rather than asking nineteen more times. Speculative requests are the last thing to send at a service that cannot answer the ones somebody is waiting for. Shutdown sets a flag the worker waits ON rather than sleeps through, or the album's several seconds would be spent inside the three second drain.
- THE USER-AGENT WAS CHECKED RATHER THAN ASSUMED, because LRCLIB asks for a name, a version and a link: `sottovoce/1.2.0 (https://github.com/matt-huang1/sottovoce)`, built from the one version definition, with the repository URL pinned against the README's clone line. It has all three and the shape matches the form their documentation gives.
- THE CHECK-MARK SENTENCE NAMED THE WRONG PROTECTION, which the entry above this one had already found and not fixed. "It is why the QMenu entries were connected to `triggered` rather than `toggled`" was wrong twice over: it names a mechanism the app no longer has, and AppKit never moves an `NSMenuItem`'s state on its own the way a checkable `QAction` does — so `triggered` was never what stopped a tick moving itself either. What that connection actually bought was the REFRESH not re-entering the handlers, because `toggled` fires on `setChecked` too. What protects the rule now is that the tick has exactly ONE WRITER: `NativeMenu.apply` calls `setState_`, reading the model, and the click path reads `is_checked` without ever writing it. Now asserted structurally rather than described, in all four places the sentence was written.

Two stages for the album warm, and a store that keeps its candidates
- THE PRICE WAS WRONG FOR THE COMMON CASE. Warming asked one search and ~19 gets for every album a single track was played from, and most albums get a track or two. So it is now two stages with a signal between them: one search for any album, and the per-track pass only once a SECOND track from the same album plays. A second track is the difference between a song somebody heard and an album somebody is listening to, and it is the only signal available for that — Spotify offers nothing else, and asking the user would be a setting for something nobody should have to think about.
- RE-MEASURED PROPERLY, and the numbers moved against the expensive stage rather than for it. Counted the way the code now stores things, over the same 4 albums and 47 tracks: stage one alone is **1 request per album for 26%** of it warm and usable; both stages are **20 requests for 34%**. The earlier "about 40%" was a looser accounting — it counted the tracks a `/get` answered rather than the tracks a strict duration check would actually serve. So the second stage buys **8 points for 19 requests**, which is a poor trade for every album and a fair one for an album being played through. That is the whole argument for splitting them, and it is stronger than the one it replaced.
- A NAME KEEPS EVERY RECORD, NOT THE FIRST ONE. LRCLIB really does answer with the same title at three different lengths, and which of them is this recording is a question nobody can answer at the time they are stored — the duration is only known when the track plays. So the store is a list per name and `read_warm` picks by duration, which is what makes stage one worth its one request at all: picking the first would have thrown away the record that matched.
- AND STAGE TWO ADDS RATHER THAN REPLACES. A `/get` answer is better sourced than a search hit, so it goes first and wins a tie, but it can also be a different recording — measured, replacing cost one of the 16 tracks the union covers. A request made to gain a track that loses one is the wrong shape.
- THE INDEX IS WHERE THE STAGE IS DECIDED, and it is on disk rather than in the window: which names the search returned, which of this album's tracks have been seen playing, and whether the per-track pass has run. That means "a second track" survives a restart, which is right — coming back to an album tomorrow is the same intent as playing on today. The window's only contribution is to consider each TRACK once rather than each album once, because a guard that stopped at the first track is the guard that hides the signal.

Publishing a sync back to LRCLIB (suite 1785 → 1803)
- THE ASYMMETRY WAS THE POINT. LRCLIB gives this app its lyrics for nothing, with no key and no account, and a sync tapped out here is exactly what it is missing for that song. Every rule in this milestone is a restriction on the way back, because "there ought to be a way" is one short step from an app that uploads somebody's work without being asked.
- ONE CASE, DELIBERATELY. LRCLIB has the WORDS for a track and no timings, and the user has made timings for it. Adding stamps to text they already host is the clean case: the lines came from them, so what goes back is their own words with times against them, attached to the track record they already have. A track LRCLIB has nothing at all for is a whole set of lyrics from somewhere, with no record to attach it to and nothing to check it against, and it is a step of its own.
- THE GATE IS ASKED TWICE AND THE TWO ARE NOT THE SAME QUESTION. `standing_refusal` is the MENU's: it reads the sync on disk, the record beside it, the cached answer and Spotify's metadata, costs nothing and works offline, and answers "is this worth offering". `verify` is the PUBLISH's and goes to LRCLIB. The cached answer is what they said the first time the song played, which may be weeks ago and may have been replaced by somebody else's contribution since; a publication is permanent and is done to somebody else's database, so the condition it turns on is checked against the database. A song can be offered and then refused, and that is the correct outcome rather than a gap.
- AND THE WORDS ARE CHECKED, NOT JUST THE TIMINGS. A sync made here has lines taken from LRCLIB's own plain lyrics, so they should be those lines exactly. One built from lyrics pasted in during an outage is a set of stamps against words nobody else has, and attaching them to LRCLIB's text would be wrong in a way nobody could see afterwards. `sync_targets(plain)` against the sync's own lines is the whole check, and it is what makes "adding timestamps to text they already host" a fact rather than a description.
- THE METADATA SENT BACK IS THEIRS, NOT SPOTIFY'S, and this is the subtlest thing in the milestone. A submission is matched to an existing track by its NORMALISED names and a duration within two seconds (`get_track_id_by_metadata_tx`, read in the server source), so Spotify's 214 seconds against LRCLIB's 213 still finds the track — but Spotify's spelling of an album against LRCLIB's different one does not, and would quietly create a SECOND track record carrying the timings while the plain lyrics stayed where they were. So the submission is built from the fresh check's own answer. Sending back what they gave us is what makes this an addition to their record rather than a near-duplicate of it.
- CONSENT IS TO CONTENT RATHER THAN TO AN IDEA. The window opens, asks LRCLIB what it is holding, and only then shows anything: the exact `Submission` that would be sent, both bodies whole and scrolling, neither summarised. The button underneath sends that one object. There is no bulk path, no queue, and completing a sync sends nothing — the first test in the integration file asserts that before it asserts anything else.
- THE PROOF OF WORK'S RULE CAME OFF THE SERVER, NOT OFF THE EXAMPLE. LRCLIB's documentation points at LRCGET's `challenge_solver.rs`, whose loop walks `0..(result.len() - 1)` and so ignores the last byte; the server's `verify_answer` walks all thirty-two. The difference only bites when the first thirty-one bytes are identical, which nobody will ever meet — and it is a difference, and this is a verification somebody else performs. The rule here is the server's, and it turns out to be one comparison: two byte strings of equal length compare in Python exactly the way the server walks them, so `digest <= target` IS "fail on a greater byte, pass on a smaller, pass when they run out". The suite transcribes the Rust loop and checks the two agree over cases chosen to break them, including a hash greater in the LAST byte alone.
- MEASURED, TWELVE SOLVES AT THE DOCUMENTED TARGET: median 4.67s, mean 7.33s, slowest 24.29s, 3.32M hashes/s, median 15.9M attempts against the 16.84M the target predicts. The spread is the shape of the thing rather than noise — each attempt is an independent coin, so the time to a hit is geometric and the tail is long — and it is why there is a progress line and a cancel rather than a spinner and a promise. It is also why no number here can promise a duration: the server divides the target down as recent submissions rise, so a busy hour is a harder challenge.
- TWO DECISIONS FELL OUT OF THAT MEASUREMENT. The hasher is primed with the prefix once and COPIED per attempt rather than rebuilt: 3.14M hashes/s against 2.01M, 56%, and the prefix is 32 bytes of every 40-odd hashed. And the deadline and the stop flag are read every 50,000 attempts rather than every attempt: at this rate a look every 15ms, costing nothing readable (3.61M/s chunked against 3.53M/s unchunked over five runs each, which is inside the noise).
- THE PROGRESS IS A COUNT AGAINST AN EXPECTED COUNT AND NEVER A PERCENTAGE. Being a third of the way through 16.8 million says nothing about being a third of the way through the work: the odds of the next hash landing are what they were at the start. What the two numbers DO say is how big the problem is, which is what somebody deciding whether to wait actually wants to know.
- A CHALLENGE THAT EXPIRES MID-SOLVE IS REPLACED RATHER THAN REPORTED AS A FAILURE, because it is preparation rather than sending, and consent governs sending. It is said out loud all the same — the seconds already spent were real — and it is bounded at three, because a target hard enough to outlast its own five minute lifetime twice running is one this machine will not beat on the third try. The solver stops fifteen seconds before the expiry so a nonce found at the end still has time to arrive.
- THE POOL LEARNED POST, AND DELIBERATELY DID NOT LEARN THE RETRY. A GET that fails on a REUSED connection is retried, because a server may close an idle socket at any moment and the question was never heard. That reasoning does not survive a POST: the failure modes are "never arrived" and "arrived, answer lost", the connection cannot tell them apart, and only one is safe to repeat. Here it matters more than usual, because the token is accepted exactly once — a resend that was really a duplicate either publishes twice or is refused for a token already spent. So a failure is reported and asking again is somebody's decision, starting from a fresh challenge.
- THE PAUSE IS ONE DOOR NOW, NOT TWO. `_refuse_while_held` and the 429 handling were lifted out of `_fetch_json` so the POST obeys them too. That is the same argument the hold was written with — it is a fact about the HOST rather than about an errand — and the failure mode without it is precise: a 429 earned by a lookup, and a publish walking straight through the pause it started. Asserted in both directions in the provider tests, and end to end in the integration tier where a 429 on the publish stops the retry that follows it.
- AND THE GAP BETWEEN REQUESTS STOPPED BEING THE WARM'S. `WARM_REQUEST_GAP_SECONDS` became `REQUEST_GAP_SECONDS`, because 200 to 500ms between sequential requests is what LRCLIB asks of a CLIENT rather than of a library scan; the publish exchange is three requests in a row and obeys the same number. One rule with no exception, which costs 350ms in front of a publish that has just spent seconds solving — the alternative is a rule with a case in it, and a case is a thing to get wrong later.
- THE RECORD OF A PUBLICATION IS A SIDECAR IN `.user_syncs/`, and where it lives was the decision. Not `.lyrics_cache/`: clearing the cache is a documented reset, and forgetting what has been published is not a reset, it is an app offering to send somebody's work a second time. Not the preferences: it belongs to the FILE rather than to this Mac, so a sync deleted by hand takes its record with it. It holds the SHA-256 of the text that was sent, so a re-sync is a different thing to send and the entry comes back for it — which is right, because the timings are what a re-sync changes and the timings are what publishing is for. One file per sync rather than one index, so a failed write can only cost one record and nothing in that directory ever truncates a file another record is also in.
- IT IS WRITTEN BY THE PROVIDER, WHICH IS THE EXISTING RULE RATHER THAN AN EXCEPTION TO IT. `test_user_sync_safety` asserts that exactly two modules in the package call `write_text`, and the new writer went into one of them rather than the list gaining a third name. The sharper half of that test also stood: `record_published` writes IN the directory and may not know `user_sync_path`, because it writes a sidecar beside the sync rather than the sync.
- THE MENU'S ANSWER IS COMPUTED WHEN SOMETHING COULD HAVE CHANGED IT, not on every render. `_refresh_menu` runs on every frame and the gate costs a stat, a file read and a hash of the sync — nothing once a song, far too much sixty times a second. So `_reconsider_publishing` runs on a track change, on a lookup landing (the cache entry it writes is half the gate, and a completed sync reloads through that path), and after a publication.
- AND THE ENTRY AND THE LINE THAT REPLACES IT ARE DERIVED FROM ONE REASON. `standing_refusal` returns the words; `publish_offered` is `not refusal` and `sync_published` is the case that refusal exists for, so the two can never both be shown and neither is a second answer to what the state is. The line is a READOUT, following the position readout's precedent: a row that states a fact rather than offering an act.
- A SECOND WINDOW AGAIN, FOR THE PASTE WINDOW'S REASON PLUS ONE. The lyrics window is frameless, refuses focus, shows without activating and is 460 points of HUD over somebody's work; what has to happen here is a person reading a whole submission and deciding whether it goes to a public database. That is not a thing to do in a HUD, and not a thing to do behind a control that could be pressed by accident. It activates the app first, like the paste window and for the same measured reason.
- THE EMPTY STATES WERE LOOKED AT AND WERE WRONG. Screenshotted in all six: at the review size, a window holding one sentence put it in the middle of 620 points of nothing, because the layout has to give the spare room to SOMETHING and with the bodies hidden the only takers were the gaps between labels. Two things fixed it and both were needed — a filler that takes the spare room, placed BELOW the status line rather than above it (above, the sentence was pushed to the bottom and the heading stayed at the top, which reads as two unrelated things), and a smaller window until there is something to read. The numbers were healthy the whole time.
- THE INTEGRATION FILE FAKES ONE OBJECT. The window is real, the click arrives through `Menu.trigger`, the publish window runs its real workers on the real pool, `publish.py` walks the real exchange, `challenge.py` really solves the proof of work, and `ConnectionPool` really pools the requests; what is faked is the connection. The song's lyrics arrive the same way as in the lyrics file — a real `PlayerMonitor` over a fake Spotify, and the real `FetchTask` writing the real cache entry — and that matters more here than anywhere, because half the gate IS that cache entry, and a test that wrote it by hand would have answered its own question.
- WHICH IS WHY TWO HELPERS MOVED. The LRCLIB connection fake and the "a song starts and the monitor notices" machinery both had a second file needing them, so they went to `helpers.py` and the fixtures to `conftest.py`, which is the rule: a helper goes there when a SECOND file needs it and not before. The fake grew a record of the whole request rather than the path alone, because publishing is the first thing here told apart by its VERB and carrying a body and a header of its own.
- THE ROUTE TABLE TAUGHT SOMETHING. The publish check asks the same `/api/get` the song's own lookup asked, so a route added up front to change the check's answer changed the SONG's answer too and three tests failed in the fixture. Which is not an accident to route around: it is the same question, and the whole point of asking it twice is that the answer may have changed in between. So the tests change what LRCLIB says AFTER the song has played, which is the situation the fresh check exists for, spelled the way it actually happens.
- THE TARGET IN THOSE TESTS IS AN EASY ONE, AND ONE OF THEM IS IMPOSSIBLE. `FF..FF` is cleared by the first hash, so the exchange runs at full speed; `00..00` is cleared by nothing, so the cancel and the shutdown drain can be driven against a solve that is genuinely running. What the real target costs is measured in `challenge.py` rather than sat through in a suite nobody would then run.

- WHAT WAS REALLY WRONG WAS THAT A TAP THAT DID NOTHING SAID NOTHING, in two different ways, and either of them is indistinguishable from a dead control. MEASURED: with playback not PLAYING the bar is disabled, and a disabled `QPushButton` SWALLOWS the press — `acted=0, dragged=0`, so the press does not even fall through to the window, and the only thing on screen that knows is the word PAUSED. None of the three said a word, and the first of those is the one that matters: A SONG ENDING IS A TRACK CHANGE, so the commonest way to reach that line was tapping the last verse of a song and having the next one start. Minutes of somebody's attention, gone, with no message and nothing on disk.
- AND THE APP ALREADY DISAGREED WITH ITSELF ABOUT THAT. `PlayerMonitor` debounces a single trackless poll because "mid item-switch AppleScript can briefly report no track"; `LyricsViewModel.player_state_changed` SUSPENDS rather than resets because "a stop can be a one-poll blip". Two layers treating a stop as provisional, and the one thing downstream of them that could not be rebuilt treating it as final.
- SO A PASS IS WRITTEN DOWN AS IT GOES, and after that the fix is arithmetic. Every tap and every undo writes `{version, lines, stamps}` to `.user_syncs/<id>.pass`. Nothing that merely ENDS a pass may take it: `_cancel_sync` became `_leave_sync` (the session goes, the journal stays) and the three interruption sites call `_end_pass(why)`, which names itself into the log and puts the count on screen.
- THE LINES GO IN THE RECORD, NOT JUST THE STAMPS, and that is what makes a resume trustworthy rather than plausible. A stamp is a number against a POSITION IN A LIST, and the list can change between one playing of a song and the next — a different lookup, a cleared cache, a re-sync from other lyrics. `resume_targets` refuses a record whose lines are not the lines in hand, which is the same rule publishing already holds itself to one layer down. A record with no lines to disagree with (a pasted pass) stands alone, because nothing else knows those words.
- IT LIVES IN `.user_syncs/` AND THAT MAKES IT THE FIRST FILE THIS APP MAY REMOVE. Not the cache: clearing `.lyrics_cache/` is a documented safe reset and minutes of tapping is not something a reset may take. Which means the deletion guard had to be narrowed rather than kept — `clear_pass` is the ONE function in the package that may unlink, asserted twice over by AST (no other file contains a deletion primitive; inside the file that does, no other function), and the path it may name is asserted to be `pass_path` alone. A journal is the only file in that directory whose whole purpose is to stop existing; everything else there is work nobody can make again.
- WHICH IS ALSO WHY THE PARTIAL MARKER IS OVERWRITTEN RATHER THAN DELETED. A complete pass has to clear the "this covers part of the song" mark, and the obvious way to do that is `unlink` — inside `save_user_sync`, the one function that knows a `.lrc`'s path. So it writes `{"digest": null}` instead. The answer changes, and the package still has exactly one deleter, and it is not the one that touches syncs.
- JOURNALLING IS ON THE UI THREAD AND THAT WAS MEASURED, not assumed: 0.059ms by median and 0.149ms at worst over the forty writes a forty line song makes, for a 2588 byte file, against a tap rate of a few a minute. Moving it to the pool would have bought nothing and cost ordering — two writes of one file able to land out of order is a way to lose the last tap rather than a way to keep it. A write that FAILS is not swallowed: it is the one case this whole mechanism cannot cover, so `_pass_unsaved` puts it on screen rather than into a log nobody is reading mid-song.
- ✕ CHANGED WHAT IT MEANS, WHICH MEANT ITS CONFIRMATION CHANGED TOO. It used to throw the pass away, so it asked "discard this sync?"; it now stops the pass and keeps every stamp, so it asks "stop here? your taps are kept". Discarding moved to the menu, and that is the right way round rather than a demotion: a control the hand reaches for by reflex should reach the safe act, and an irreversible one should cost a look. Both new entries carry the count in their labels, because "save the sync so far" and "discard" are the same sentence with the number left out.
- COMPLETION STILL MEANS EVERY LINE, AND STOPPING SHORT STOPPED MEANING LOSING. Those were one rule and they should never have been. A pass kept early writes a real `.lrc` of the lines it timed — the song comes back synced that far, and following it that far is worth having — marked partial in a sidecar. The one place a half-timed song would do harm is somebody else's database, and `standing_refusal` refuses it there by NAME rather than leaving it to `verify`'s word check to refuse it by accident: a song offered and then refused is correct when only LRCLIB could have answered, and this answer is entirely our own.
- THE PARKED ENTRY WAS RIGHT ABOUT THE WRONG THING. "Partial saves" was parked to keep the storage story simple — every `.lrc` a complete timing of a whole song — and the price of that simplicity turned out to be paid by the user, in whole passes, silently. What is parked now is narrower and truer: starting a sync MID-SONG, and per-line editing of an existing sync. Resuming a pass of your own is neither.
- AND THE TESTS THAT MISSED ALL OF THIS MISSED IT THE SAME WAY THE LOOP TESTS ONCE DID. Every sync test handed the session its stamps — `session.stamp(4.0)` — which is the caller answering its own question, and a pass whose stamps arrive that way never meets the tap bar, never meets the player and never meets the things that end it. `test_window_sync_pass.py` supplies no stamp at all: a real `PlayerMonitor` over a fake Spotify carries every position, every stamp comes from a press Qt routes to the bar's live centre, and the track change, the stop, the ✕ and the layout swap are each DRIVEN rather than called.
